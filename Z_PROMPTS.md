# Z_PROMPTS: reusable prompts for working on Nerd Genie

This file holds three prompts a person pastes into a fresh AI agent session, one at a time. Each prompt is complete on its own: it names every file the agent must read, every command it may run, and the shape of the report it must give back. Copy one section from its heading down to the line of dashes that ends it, and paste it as the first message of the session. The pattern is borrowed from the HomeRecon project's `Z_PROMPTS.md`.

Everything in this file assumes the agent is running on the Linux development machine, `jared-irene`, with this repository checked out at `/home/jared/Code/coeus`. That is the only machine with the local model, the sandbox tools, the visible Chrome window, and the signed-in command-line programs the tests need. Nothing in this repository is built or tested anywhere else.

The last section, "Drift found on 2026-09-05", is not a prompt. It lists the places where the documents had fallen out of step with the code or with each other on the day this file was written.

## 1. Onboarding: "get up to speed on Nerd Genie"

You are joining Nerd Genie. It is an open-source AI agent written in Go that runs on a Linux machine. A person talks to it in a terminal or through the Signal messaging app, and it does work for them with tools: reading and writing files, running commands, using a real Chrome browser, and driving the desktop. What sets it apart is how it remembers. Every other agent we studied keeps the whole conversation as one long transcript, re-reads it on every call to the model, and summarizes it when it grows too long, losing whatever the summary left out. Nerd Genie instead keeps a short task record, shaped like a U.S. Army operations order, that says what the user asked in the user's own words, what done looks like, what has been corrected, what the plan is, what has been decided, and what has failed. The record stays under three thousand tokens however long the task runs, and the model reads it on every call instead of a transcript. A token is a piece of text about the size of a short word; models are priced and sized by tokens.

### The hard rules, in my own words

These come from `CLAUDE.md`. Follow them exactly. A rule you cannot follow is a reason to stop and report, not a reason to work around it.

- **Tests first, every time.** Write the test, watch it fail, write the code, watch it pass. The commit history shows the order: run `git log --oneline -30` and you will see a commit that begins "Failing tests:" followed by the commit that makes them pass. A test written after the code is rewritten. Every package has four kinds of test: unit; integration, under the build tag `integration`, which needs the real SQLite file in a temporary home; functional, in `test/functional/`, which drives the whole program through the same socket the terminal uses with the fakes from `internal/testkit`; and fuzz, with `testing.F`, on anything that parses text from outside the program. Line coverage must be above ninety percent per package, except the terminal screen in `internal/tui` and the two TypeScript workers, which must be above seventy.
- **Keep it simple and build only what is needed now.** The simplest thing that passes the test is the right thing. No abstraction until its second use exists, no configuration option until a real user needs it, no feature because it might be useful later. A package has one job that fits in one sentence in its `doc.go`.
- **Plain English.** Identifiers say what they are. Comments are complete sentences. Error messages say what went wrong and what to do. Documents follow the same rule, with technical terms explained on first use. The style checker in `make check` enforces this for code, and a person enforces it for documents.
- **Bound everything.** Every loop has a limit, every wait a timeout, every buffer a cap, every outside call a failure path. The bounds are named constants near the top of the file that uses them, each with a sentence saying why that number, and many are pinned by a test that fails if the number changes.
- **Every shared interface lives in `internal/contract`.** If two packages need the same interface, type, or constant, it goes there and nowhere else. The fakes in `internal/testkit` and the real implementations are written against the same lines, and every fake has a contract test that also runs against the real thing under the `live` tag, so fakes cannot drift.
- **Never edit `cmd/nerdgenie/main.go` or `cmd/nerdgenie/serve.go`.** Those two files register subcommands and wire the packages together, and the orchestrator owns them. A new subcommand goes in its own file under `cmd/nerdgenie/`, a new slash command is exported as a `contract.Command` value, and you ask for both to be registered. Never touch a package another worker owns this wave. If you need something from a neighbouring package that is not in `contract`, your brief is wrong: stop and report.
- **Go for the agent, TypeScript only for `worker/browser` and `worker/desktop`, nothing else.** Standard library first. A new dependency needs a one-line reason in `docs/DEPENDENCIES.md` and a yes from the orchestrator before it is added.
- **Borrow designs, not code.** Read the reference file your brief names in one of the other agents' code bases, understand it, and write it fresh in Go. Never copy lines. Name the borrowed design and its path in a comment at the top of the file.
- **Nothing on the user's ask-me-first list without a yes, nothing secret in the model's context, everything logged.** The permission function, the vault resolver, and the event log exist to enforce these three. Do not route around them.
- **Keep the docs honest.** When you change a package's job, interface, or dependencies, update its section of `ARCHITECTURE.md` in the same branch. After adding or moving files, run `make repo-map`. `make check` fails if either is stale.

### A task record, a job, and the working context

A task record is the state of one sitting of work, thirty seconds to an hour, held under three thousand tokens in four parts: the goal (the ask word for word, why, and a done list of at most five lines, each pointing at the result that proves it), the rules (corrections in the user's own words and a stop list), the work (the situation, a plan of at most ten steps, and one line per tool result with an id like `r7`), and the lessons (decisions with reasons and failures with causes). A job is work too big for one sitting: a record with the same four parts whose plan is a list of tasks instead of steps and whose results are the reports of the tasks that have finished, run one task at a time and reported to the user after each, with a short name the model gives it, and a job with a schedule simply has its tasks made by the clock. The working context is the text actually sent to the model on one call, built fresh every time from the layers that change least to those that change most (the harness instruction text, the persona, the tools, the job summary if there is one, the record's goal and rules, then the record's work and lessons, pinned evidence, recent messages, and a three-line memory hint), and sized to the model's window, so a big model gets most of a million tokens of recent results and a small model gets a few thousand while the record and everything above it stay the same on both.

### Step 4: reading the event log

Everything the program did is in one SQLite file, `$NERDGENIE_HOME/nerdgenie.db`. Open it read-only, with the `mode=ro` address below, so a running `serve` is never disturbed. The `events` table has five columns: `sequence`, a number that only grows; `occurred`, the time in UTC as text; `task_id`, the task's number as text such as `6`, or `j3` for a job, or empty; `kind`, one of eight words; and `body`, the event's own fields as JSON. The eight kinds are `message`, `tool call`, `tool result`, `permission decision`, `file change`, `record change`, `checkpoint`, and `reply`. A `checkpoint` is saved once per model call and its body has three fields: `number`, `askFrom`, and `text`, where `text` is the printed record exactly as the model sees it. For a task, the first line of `text` is the header, such as `# task 6   running   from terminal   no budget`, and the second line is the cost line, `this turn: 9.1k tokens in, 4.5k of them cached, 0.2k out`, where `9.1k` means about 9,100. A job's checkpoint has a header of its own, such as `# job 3   waiting   1 of 11 tasks done   next: task t2 now`, and no cost line. A `tool call` body has `ID`, `Name`, and `Input`; a `tool result` has `id`, `summary`, and `text`; a `reply` has `text`.

```python
import json, os, re, sqlite3
home = os.environ["NERDGENIE_HOME"]
con = sqlite3.connect(f"file:{home}/nerdgenie.db?mode=ro", uri=True)
cost = re.compile(r"this turn: ([\d.]+)k tokens in, ([\d.]+)k of them cached, ([\d.]+)k out")
task = "6"
rows = con.execute("select sequence, occurred, kind, body from events where task_id = ? order by sequence", (task,))
for sequence, occurred, kind, body in rows:
    body = json.loads(body)
    if kind == "checkpoint":
        lines = body["text"].splitlines()
        found = cost.search(lines[1]) if len(lines) > 1 else None
        print(sequence, occurred, lines[0], found.groups() if found else "no cost line")
    elif kind == "tool call":
        print(sequence, occurred, "call", body["Name"], json.dumps(body["Input"])[:80])
```

Print the last checkpoint's `text` in full for every task and read it as a person would.

### Step 5: the long run, and what to measure

Give it a task that takes tens of rounds. The trial checklist in `docs/TRIAL.md` uses "build a small snake game in a new folder: a plan, the HTML, the CSS, the JavaScript, and a README, then a note of what is left", which should land as a job with a task list rather than one flat task. Drive it with `nerdgenie run --wait` and a generous `--timeout`, and watch it in `nerdgenie tui` from a third terminal at the same time. When it ends, measure these from the log, one row per round (one round is one checkpoint):

- **Start with the report.** Copy the home's `nerdgenie.db`, its `-wal` and `-shm` beside it, into a scratch folder and run `go run ./scripts/runreport --log <the copy> --task N`; never point it at the file the agent is writing. It prints the rounds and minutes, the calls by tool, how many replies asked for more than one tool, how many rounds only wrote the record or only ran the tests, the tokens in and cached and out, and the rewinds and failures. Those are the numbers `docs/PROGRESS.md` carries from the fifth Tetris build on, and the ones below are how to read them by hand when you need the round-by-round view.
- **Prompt size per round**, the "tokens in" figure. It should hold roughly flat across the task, since the record stays small and the window of recent results slides. A prompt that grows round by round means the window is not sliding or the record is not being held to its size.
- **Cached share per round**, cached divided by tokens in. After the first round it should be high; `docs/PROGRESS.md` measured 84, 86, and 87 percent of the prompt shared between consecutive rounds at rounds 10, 20, and 30 of the forty-step fixture. A drop to near zero in the middle of a task means something above the cache line was rewritten, and that is a bug worth the sequence numbers around it.
- **Seconds per round**, the difference between consecutive checkpoints' `occurred` times. Cross-check it against the daemon's own log at `~/llm/logs/19091.log`, which you only read. Each call leaves a line like `prompt eval time = 8345.78 ms / 2776 tokens (3.01 ms per token, 332.62 tokens per second)`: the token count there is what the card had to read afresh on that call, not served from its cache, and the harness's "of them cached" figure should account for the rest. The `eval time` line beside it is the model writing its reply at about fifty-six tokens per second, and `total time` is both. So a round that reads three thousand tokens afresh and writes three hundred should take about fifteen seconds; a round far longer than that arithmetic is a hung tool (the tool deadline is seven minutes), a permission preview waiting for a yes, or the daemon serving someone else. The log is shared, so match calls by time, and remember that `grep 'prompt eval time'` over the whole file counts everybody's calls.
- **Rounds per task**, the number of checkpoints with that `task_id`. Expect tens, not hundreds. A tic-tac-toe game on this model took 24 and 55 calls in `QWEN_BENCHMARK.md`; a Tetris build once ran 145 rounds with no plan and no done list, and that number is the failure.
- **The record at the end.** Read the last checkpoint's `text` for each task and answer four yes-or-no questions: does the plan have check marks with result ids on the finished steps; does the done list have a line for each thing that must be true, each pointing at a result; are there failures with causes under Lessons; and, if the model ran a test runner, is there a situation line carrying the last run's counts (that line is written by the harness, `internal/loop/teststate.go`, from the runner's own summary).

### What the harness does on its own now, so you can tell a bug from the design

After every write or edit of a JavaScript, Python or Go file the harness runs the language's checker and, once the model has run the tests once, the tests, and puts both on the change's own result. Rounds in which nothing measurable moved are counted in the Situation as "rounds since progress"; ten earn one line, twenty clear the conversation with the stall written into the record as a failure, and twenty more stop the task. A call repeated with only its intent reworded is a repeat. A stopped or failed task is carried on by the next message. A browser result carries the page's errors, a click that changed nothing says so, a page whose script never yields is named as such with the loops in the changed scripts listed, and `browser_read` answers a question about a page served from this machine through its `ask` field. `pkill`, `killall` and `pgrep` are refused. Seeing any of these is the harness working, not a fault.

Since the night of 5 September the harness also: lists the loops of a page whose script hangs, from the scripts the page loads and the modules they import, `while` first, with the loop whose body never touches its condition marked and kept on the situation's browser line until the page answers again; refuses a failure the record already holds and a plan step already done, cuts every lesson to one line and keeps the newest eight; counts a browser read with a new intent, and the first edit of a file, as progress; answers a pin or a step mark with what each named result says; takes any result label the record reached as proof; reads a past result from an offset like a file; saves every screenshot under the home's `run/screenshots` folder and says the model reads words in its place; lets the model read the spill and screenshot folders inside its home; keeps the word "refused" on a tool line whatever the argument's length; and takes an ask of up to two thousand characters.

### Known failure shapes to look for

- **The same call repeated.** Consecutive `tool call` events with the same `Name` and `Input`. The guard allows a second identical call and refuses it with a message, and ends the turn at a hard cap; the numbers are `IdenticalCallsAllowed` and `SameCallHardCap` in `internal/loop/guard.go`, and on the screen a repeated call is counted on its pill as "× N". Three or more of the same call in a row is a finding.
- **Throwaway debug scripts.** `file change` events or `write` calls that make files such as `debug.js`, `test1.mjs`, or `tmp.py` that are not in the plan and are still in the work folder at the end.
- **A job put down on a trailing question.** A job task whose reply ends with a question mark while its done list is fully proven, so the job header reads `waiting` and no next task starts. The done-check now runs before the question is read (see `git log` for 2026-09-04), so if you see it, it is a regression: report the job's checkpoint header and the reply's sequence number.
- **A record with no done list.** A task whose last checkpoint has `Done when:` with nothing under it, or a task that ended `waiting` because a reply with no done list was read as a question rather than an answer.
- **A review answer saved as tool markup.** After a task worth reviewing, a memory fact or a skill whose text is `<tool_call>` markup or a JSON object rather than a sentence. You have changed something in Nerd Genie, or you are checking a change someone else made, and your job now is to bring the documents back in line with what the code does today. ### The rule for a changed package

If your branch changes a package's job, its interface, its dependencies, or one of its bounds, its section of `ARCHITECTURE.md` changes in the same branch. Not the next branch, not at the gate. Read the section top to bottom against the code and fix what is no longer true: the one-sentence job, the exported names, the imports, the numbers, the borrowed design. If the section does not exist because the package is new, write it in the same shape as its neighbours, and add the package to the table under "Packages and their one-sentence jobs" in build order. If you added, moved, or removed a file, run `make repo-map` and commit the regenerated `REPO_MAP.md` in the same branch. `make check` fails on a stale map, and the orchestrator reads `ARCHITECTURE.md` against the code at every gate.

### Adding a row to the check table

The check table in section 14 of `NERDGENIE.md` has four columns: what Nerd Genie does, the design section that says so, the brief that built it, and the test that proves it. A row is added when a claim is added to the document or when a behaviour worth promising lands with its test. To add one:

1. Write the claim in the first column as one plain sentence that a person could check.
2. Find, or write, the sentence in `docs/NERDGENIE_PLAN.md` that says the same thing, and put its section number in the second column. If the design does not say it, the design is changed first.
3. Put the brief number from `docs/WORK_PLAN.md` that owns the work in the third column, such as `3.1` for the loop.
4. Put the test's exact function name and its file in the fourth column, such as `TestAProvenDoneLineChangesNothingAboveTheCacheLine` in `internal/context/donelisttail_test.go`, and confirm with `grep -rn "func TestName("` that it exists.

If any one of the three, the design sentence, the brief, or the test, is missing, do not patch it in the wrong place. Report the gap.

### Keeping the instruction text

Section 5 of `docs/NERDGENIE_PLAN.md` is the text the model reads first on every call, and it must stay under five hundred words and identical to the constant in `internal/context/instructions.go`. Two tests hold it: `TestTheInstructionTextIsTheDesignsOwnWords` compares the constant to the design's block quote word for word, and `TestTheInstructionTextIsSmallEnoughToRideInEveryPrompt` counts the words of the text plus the skill-list heading in `internal/context/skills.go` against `MaxInstructionWords`, which is 500. To change it, edit the block quote in the design first, then copy it into the constant exactly, then run `go test ./internal/context/`. Nothing goes in without something coming out: the comment above the constant records every trade made so far, and a paragraph added is a paragraph read on every call to every model. Keep every sentence short. The same discipline applies to the example record in section 4 and the golden file in `internal/record`: change the design, then the golden file, then run `go test ./internal/record/`.

### Recording what happened

`docs/PROGRESS.md` gets a paragraph under the current wave for anything a person would want to know next week: what was built, what it changed in a contract, what a live run cost in tokens, and what a trial found in the person's own words. Numbers come from the event log or the daemon log, with a date. Do not tidy old sections.

### The checklist

1. Every package your change touched has a true section in `ARCHITECTURE.md`, and a new package is in the package table in build order.
2. `make repo-map` has been run if any file was added, moved, or removed, and `REPO_MAP.md` is in the branch.
3. Every claim your change added or altered is a row in the check table with a design section, a brief, and a test that exists.
4. If the instruction text or the example record changed, the design changed first, the code copies it word for word, and `go test ./internal/context/ ./internal/record/` is green.
5. A number that appears in more than one document (a threshold, a cap, a port, a model name) is the same in all of them, and matches the constant in the code.
6. `docs/PROGRESS.md` has a dated paragraph if the change is a wave, a live run, a trial, or a contract change.
7. Every sentence you wrote is a complete plain-English sentence with its technical terms explained on first use, and nothing was copied from another project's documents.
8. `make check` is green.
