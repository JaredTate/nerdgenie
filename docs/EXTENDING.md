# Extending Coeus

Coeus has four places where new pieces plug in, and nowhere else. They are a chat service, a tool, a skill, and a model provider. Design section 6 calls them the extension points, and it makes one promise about each of them: adding one is a new file written against a contract, and it does not touch the agent loop, the task record, the permission function, the memory, or the event log. Those five are the core, and the core is closed on purpose.

A contract, here, is a Go interface in `internal/contract`. That package holds every interface, type, and constant that crosses a wave boundary, and it depends on nothing. Beside it, `internal/testkit` holds one fake for each of those interfaces, and beside each fake a `Check` function that takes the **interface** rather than the fake and asserts the properties the contract promises. That is the shape of the work in every section below: implement the interface, test against the fake, and run the check on your own implementation. Because the check takes the interface, the same function that proves the fake honest proves your new piece honest.

Two rules apply to all four. **Never edit `cmd/coeus/main.go` or `cmd/coeus/serve.go`.** Those two files are the orchestrator's; a new subcommand goes in its own file under `cmd/coeus/`, and a slash command is exported from your package as a `contract.Command` value for the orchestrator to register. And **write the test first**: unit tests in `*_test.go`, integration tests behind `//go:build integration`, functional tests in `test/functional/`, and a fuzz test on anything that parses text from outside. `make check` is the gate.

## 1. A chat service

A chat service is anything a person can talk through: the terminal, Signal, and later Telegram, Slack, or iMessage. Coeus calls one a **channel**, and every channel does the same six things, so the agent loop never knows which one it is talking to.

- **The contract** is `contract.Channel`, in `internal/contract/channel.go`. Its seven methods are those six jobs plus its own name: `Name`, `Receive` (a stream of `contract.Inbound` messages that closes when the context is cancelled), `Send`, `SendFile`, `ShowPreview` (show exactly what is about to happen and wait for once, always, or reject), `AskSecret` (a prompt that hides what is typed), and `Health`. A service that cannot hide what is typed returns `contract.ErrNoMaskedPrompt` from `AskSecret` rather than reading a password in the clear; Signal does exactly that.
- **The fake** is `testkit.NewFakeChannel(name)`, in `internal/testkit/channel.go`. It gives every attach its own stream, records what was sent, and lets a test push a message in with `Push`.
- **The check** is `testkit.CheckChannel(ctx, channel)`. Call it from a unit test on the fake and from a `//go:build live` test on the real service, so the two cannot drift.
- **Where the file goes.** One new package, `internal/<service>`, importing `internal/contract`, the standard library, and nothing else of Coeus. Export a constructor that returns the channel. `cmd/coeus/serve.go` builds it and attaches it to the router and the event stream; a helper subcommand, such as linking an account, goes in its own file under `cmd/coeus/`. Nothing else changes: every message a channel receives goes into the same queue, and every reply comes off the same event stream.
- **The worked example** is `internal/signal`, whose channel is `internal/signal/channel.go` and whose linking subcommand is `cmd/coeus/signal.go`. Its section in `ARCHITECTURE.md` is the fuller account.

## 2. A tool

A tool is one thing the harness can do for the model, such as reading a file or counting words. There are eighteen built in, and a user adds more by dropping an executable into a folder. Every tool, built-in or user-written, goes through the same permission function.

- **The contract** is `contract.Tool` and `contract.ToolSpec`, in `internal/contract/tool.go`. A specification is a name, a plain-English description saying when to use the tool and when not to, the input fields with their types, and one or more permission classes: `R` reads, `W` writes, `X` runs a program, `N` uses the network, and `I` cannot be undone. The description is capped at `contract.MaxToolDescriptionWords`, which is forty, counted the way `contract.DescriptionWordCount` counts it, because a description the model reads on every call has to earn its tokens.
- **The user-tool protocol** is the whole of `internal/contract/usertool.go`, and it is three sentences long. Put an executable in `~/.coeus/tools/`. The harness runs it once at startup with `contract.UserToolDescribeFlag`, which is `--describe`, and reads a JSON `contract.ToolSpec` from its standard output. When the model calls the tool, the harness runs the same program again with one JSON object of the model's arguments on its standard input and reads the result as plain text from its standard output. `contract.DecodeUserToolSpec` is the reader, and it refuses a description with no name, a name with a space in it, no description, an unknown permission class, or a field with no name. A description over the cap is refused with this line, word for word: `the description of "wordcount" is 41 words, so cut it to 40 or fewer`. One bad script is skipped with a logged line naming the file and the problem, and the agent still starts.
- **The fakes** are `testkit.NewScriptedTool(spec, outputs...)` and `testkit.NewFakeToolRegistry(tools...)`, in `internal/testkit/tools.go`. **The check** is `testkit.CheckToolRegistry(ctx, registry)`, which asserts that every listed tool can be looked up and that every specification is one the model can read.
- **Where the file goes.** A user tool is one executable in `~/.coeus/tools/`, and nothing in the repository changes. A tool that ships with Coeus is one folder under `internal/tool/`, implementing `contract.Tool` against `internal/contract` alone, and `internal/tool`'s registry builds it. `serve.go` picks up neither: the registry reads the tools folder itself at startup, and `Specs` is what goes into the prompt.
- **The worked example** is `examples/tools/wordcount/wordcount`, a shell script of a few lines with a `README.md` beside it, and `test/functional/extending_test.go` drives it end to end through the real registry.

## 3. A skill

A skill is a saved procedure for one kind of job, the way a recipe card is a saved procedure for one dish. It is a folder, so people share skills by sharing folders, and replaying one costs no model call at all.

- **The contract** is `contract.Skill`, in `internal/contract/skill.go`: `List` (the names and one-liners that ride in every prompt), `Load`, `Run`, `Save`, and `Match`, which the router asks on every message to see whether a skill's trigger words fire. `contract.SkillSummary` is the name and the one line; `contract.SkillMatch` is what the matcher found.
- **The folder** holds four files. `SKILL.md` is a heading with the skill's name, one line of description under it, a `## Triggers` section of bullets, and a `## Permissions` section whose only four keys are `browser profile`, `site`, `daily limit`, and `irreversible step`. `steps.md` is a numbered list whose numbers must run one, two, three, each step carrying `tool:`, `input:`, and `expect:` lines; in its place a skill may carry an executable named `script`. `test.md` is the dry run. `CHANGELOG.md` records every change with a way to undo it.
- **The fake** is `testkit.NewFakeSkill()`, in `internal/testkit/skill.go`. It holds skills in memory, matches their trigger words, and records which of them ran, so a test can prove a skill ran without the model being called. **The check** is `testkit.CheckSkill(ctx, skills)`.
- **Where the folder goes.** One folder per skill under `~/.coeus/skills/`, which is `contract.Home.SkillFolder(name)`. `internal/skill` loads it, registers the websites in its permissions block as standing approvals, and puts every step through the permission function. `serve.go` registers one thing, the `/skills` command that `internal/skill` exports as a `contract.Command` value.
- **The worked example** is `internal/skill/testdata/skills/news-headlines/`, a complete four-file folder used by that package's own tests, and the skills section of `ARCHITECTURE.md` explains each file in turn.

## 4. A model provider

A provider is the piece that sends the prompt to a model and brings the reply back, streaming the text as it is written and reporting what the call cost. Three of them cover nearly every model in existence, so a fourth is rarely needed; when it is, it is one file.

- **The contract** is `contract.Model`, in `internal/contract/model.go`: `Name`, `ContextLength`, and `Send`, which takes a `contract.Request` and an optional callback for each piece of text as it arrives, and returns a `contract.Reply`. A request carries the system prompt as ordered `contract.SystemBlock` values with the three cache boundaries marked on them, the messages, the tool specifications, whether tools are off, and the output cap. A reply carries the text, the tool calls, why the model stopped, and a `contract.Usage` whose `CachedInputTokens` is a part of `InputTokens` rather than an addition to it.
- **Two errors are part of the contract.** Return `contract.ErrContextOverflow` when the request was longer than the window, because nothing but the context builder can fix that and no retry should be attempted; return `contract.RateLimitedError` with a `RetryAfter` when the provider asked the caller to wait.
- **The fakes** are `testkit.NewFakeModel(script)`, which plays a `testkit.Script` of steps and fails a call whose request lost something the step said must still be in it, and `testkit.NewFakeProviderServer(script)`, which speaks both wire protocols on a loopback port and can stall, rate limit, fail, overflow, or break its stream part way through. **The check** is `testkit.CheckModel(ctx, model)`.
- **Where the file goes.** One new file in `internal/provider`, and one new value of `contract.ProviderKind` beside the four that exist: `anthropic`, `openai` (any OpenAI-compatible server at a base address, which already covers llama-server, LM Studio, Ollama, and every cloud gateway), `codex` (the Responses API on OpenAI's ChatGPT backend, signed in through the `codex` program's own file), and `cli` (the vendor's own signed-in command-line program). `provider.New` chooses by the kind on the `contract.ModelAlias` it is given. Nothing in `serve.go` changes: the user names the new alias in a `[[models]]` block in `config.toml`, with `default_model` and `fallback_chain` pointing at it.
- **The worked example** is `internal/provider/openai.go` with its wire shapes in `internal/provider/openaiwire.go` and its stream reader in `internal/provider/openaistream.go`, and the providers section of `ARCHITECTURE.md` says what each of the three does differently.

## What is not an extension point

The agent loop, the task record and its rules, the permission function, the four kinds of state, and the event log have no extension points, and keeping them closed is what keeps the agent simple. If a change seems to need one of them opened, that is a brief for the orchestrator, not a file for a contributor. In the same spirit, there are no plugins loaded into the agent's own process: a user tool is a separate program, and a skill is a folder of text.
