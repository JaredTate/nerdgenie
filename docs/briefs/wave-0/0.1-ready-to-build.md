## Step 4: `internal/contract`, in full

This is the package everything else is written against. It imports nothing outside the standard library and nothing from this module. Every exported name has a doc comment that is a complete sentence. Group it in files by subject (`model.go`, `tool.go`, `channel.go`, `record.go`, `config.go`, `socket.go`, and so on), each under five hundred lines. Keep the shapes minimal; every field must be needed by a brief in `docs/WORK_PLAN.md`. Where you must choose, choose the simpler Go. What each must hold:

- **`Model`**: `Name()` (the alias from configuration), `ContextLength()` in tokens, and one call that sends a `Request` and streams the reply: text deltas arrive through a callback as they are produced, and the return value is the full `Reply` with the text, the tool calls, the finish reason (end, tool calls, length, stopped), and the `Usage` of tokens in, out, and cached. A `Request` holds the system prompt as an ordered list of blocks where a block may mark a cache boundary (design section 4 names three, A, B, C), the messages (role, text, tool calls, tool results), the tool specs, whether tools are off, and the output cap. The system blocks carry, in order, the harness rules and persona (boundary A), the tools (boundary B), the job summary when the task belongs to a job, and the record's goal and rules (boundary C); the provider decides how to express a boundary on the wire. A tool call has an id, a name, and raw JSON input. A tool result has the call id, text, and an error flag. Define sentinel errors the provider brief needs: context overflow (never retried), rate limited with a retry-after duration, and a stalled stream.
- **`Tool`**: `Spec()` and `Run(ctx, input json.RawMessage) (ToolOutput, error)`. A `ToolSpec` has the name, a description (the registry rejects over forty words), the input fields (name, type, description, required), and the permission class as a set of the letters in design section 7: read, write, execute, network, irreversible. A `ToolOutput` has the text and, when the output was over the cap, the path the rest was spilled to.
- **`Channel`**: `Name()` and the six things from design section 6: receive (a stream of inbound messages: id, sender, text, attachment paths, time, and the channel name), send text, send a file with a caption, show a preview and collect a decision, show a masked prompt and return the secret (or a sentinel error when the channel cannot), and health.
- **`Permission`**: decide on a request (the tool name, the input, the reduced command prefix, whether the run is unattended) and return allow, ask, or deny with a reason and the preview text; and remember an answer for the session: once, always, or reject with a reason. Include the shipped ask-me-first list of three entries as constants, named in plain words.
- **`Memory`**: search, get, save (a batch), and hint (three lines for a query). A fact has an id, text, source, date, and the id of the fact it supersedes, if any.
- **`Command`**: a struct value, not an interface: the name without the slash, a one-line help, whether it is terminal-only (the vault), and a run function taking the argument text and a small context (the channel to answer on, the task id if any) and returning the reply text. Packages export these as values and `serve.go` registers them.
- **`Skill`**: list (name and one-liner for the prompt), load (the body), run, save (a folder), and match (the trigger matcher the router calls; returns the skill name and whether one matched).
- **`Job`**: create a job (with or without a schedule), add a task to it, list jobs, run one now, pause one, switch one off. A job is a piece of work too big for one sitting, design section 4 "The job record": it has the same four parts as a task record, but its plan is a list of tasks (each with a task id, a done flag, a report id like `j4.2` when done, and a date when it must wait for one) and its results are the tasks' reports. A job may carry a schedule (one of at, every, or cron, plus a timezone) and a task template; a scheduled job creates one task per tick. Its header carries the progress line ("3 of 12 tasks done") and the next due task. State: running, paused, off, done; last run; next run; failures in a row.
- **`Sandbox`**: available (an error saying why not when bwrap is missing) and run a command (program, arguments, working directory, environment, timeout, standard input) returning standard output, standard error, the exit code, and whether it timed out.
- **`Secrets`**: resolve a `secret://name` reference into a credential the harness uses (site, domains, username, password, TOTP secret) and never hands to the model; get the sudo password; redact text.
- **`BrowserWorker`**: the eleven methods of `worker/browser/PROTOCOL.md` as Go methods with typed parameters and results, plus `Close()`. The snapshot and diff types from the protocol live here.
- **`Desktop`**: launch or focus an app, screenshot with numbered marks, click a mark, type text, press a key combination, drag from one mark to another, get and set the clipboard.
- **`Clock`**: now, sleep with a context, and a ticker.
- **`Store`**: the event log's shapes. An event has a sequence number, a time, a task id, a kind, and a JSON body. The kinds are the ones brief 1.1 lists: message, tool call, tool result, permission decision, file change, record change, plus checkpoint and reply. Write is one append returning the sequence number; read is by task, by kind, by id, or by range; replay hands events back in order to a function.
- **The record types**, exactly the four parts of design section 4 with the example task record and the example job record as the guides: the header (the kind, task or job; the id; status; origin; for a task the budget line and the cost line; for a job the progress line and the next due task), the goal (the ask, the why, the done list with a result id or user reply behind each line), the rules (corrections with ids like `C1`, the stop list), the work (the situation lines; for a task the plan steps with a check mark and result id, for a job the task list with a task id, a check mark, a report id, and a date; the result lines with ids like `r7`, or for a job the report lines with ids like `j4.2`, each with a one-line summary), and the lessons (decisions with a reason, failures with a cause). One set of types serves both kinds; the kind field says which. The parser and printer are brief 1.2's; you define only the types and the id formats.
- **The configuration struct** with every field brief 1.3 names and its default in the doc comment: the model aliases (each with provider kind, base address, model name, context length, key reference), the default model, the fallback chain, the local model alias whose default points at `http://127.0.0.1:19091/v1` with model name `local-coder` and context 262144, the Signal account, the browser profile path, the sandbox roots (never `~/.nerdgenie`, the vault, the browser profile, or `~/.ssh`), the backup path, the search server address, the handoff timeout, and the caps from the design: one hundred rounds, one hour, seven minutes per tool, fifteen minutes per turn, one hundred queued messages, the tool output cap, the identical-call window of twenty, the memory file caps. A function returns the struct with defaults filled.
- **The exit codes**: 75 restart me, 78 bad configuration.
- **The tool names** as constants: the eighteen from design section 7, including `job` (not `schedule`) and `task`.
- **The socket message types** from `ARCHITECTURE.md`: from the screen `message`, `command`, `approve`, `deny`, `secret`, `attach`, `detach`; from the program `delta`, `reply`, `preview`, `ask`, `handoff`, `status`, `error`; one envelope struct with a type field and the payload fields each type needs, and the socket path under the home folder.
- **The home folder layout** from `ARCHITECTURE.md` ("Data on disk") as path helpers from a root, and the file modes.
- **The user-tool protocol**: the `--describe` flag, the JSON it must answer (the `ToolSpec` shape), input as one JSON object on standard input, output as text on standard output, and the folder `~/.nerdgenie/tools/`.

Tests for `contract`: it has almost no logic, so its tests are small: defaults are what the doc comments say, the sandbox root exclusions hold, id formats are what the design shows, and every exported identifier has a doc comment (the style checker enforces this too).

## Step 7: `internal/lint`, the style checker

A library that walks Go packages with `go/parser` and `go/ast` and reports violations, wired into `make check` through `scripts/stylecheck`. The rules, each with its own name so a message can say which one:

1. **Comment sentences.** Every comment on a declaration starts with a capital letter and ends with a period, question mark, or exclamation mark. A `//go:` directive, a `//nolint` line, and a URL line are not comments for this rule.
2. **Doc comments.** Every exported identifier has a doc comment. Every package has a `doc.go` whose first comment sentence begins with `Package <name>`.
3. **Function length.** No function body is longer than sixty lines.
4. **File length.** No file is longer than five hundred lines.
5. **Error messages.** Every string passed to `errors.New` or as the format to `fmt.Errorf` starts with a lowercase letter, does not end with punctuation, and has at least four words, because an error must say what went wrong and what to do.
6. **Identifier names.** No identifier of one letter except loop indices, receivers, and the conventional `t`, `b`, `f`, `r`, `w` in tests and handlers; no identifier that is an abbreviation from a short fixed list (`cfg`, `ctx` is allowed, `msg`, `req`, `resp`, `buf`, `tmp`, `str`, `num`, `val`, `err` is allowed).
7. **Borrowed design header.** A file whose top comment mentions a reference project must also name a path (`~/Code/...` or `docs/reference/...`).

Tests: a fixture tree under `internal/lint/testdata/` with one file per violation kind, and a clean file; the checker reports exactly one violation for each bad file, with the rule name, and none for the clean one. Run the checker on the real repository as part of your own definition of done.
