# Brief 1.1: the event log

Before you write anything, read these five files in this order: `CLAUDE.md` for the rules and the commands, `COEUS.md` for the plain-words explanation of the state design and the check table that ties each claim to a brief and a test, `ARCHITECTURE.md` for how the code is put together and what earlier waves built, `REPO_MAP.md` for where everything lives, and `docs/COEUS_PLAN.md` for the design you are implementing, especially the section this brief names. Then read this brief and the reference files it points at. You own exactly one package. Write the tests first.

## The package

`internal/log`. One sentence: the append-only event log in SQLite that is the truth about everything that happened. Design section 4, "History", and section 11, "Reliability" (the log is the ledger; a reply is logged before it is sent; after a crash the agent replays the log). The plan text is `docs/WORK_PLAN.md`, Part 3, Brief 1.1. This package implements `contract.Store`; read `internal/contract` for the exact `Event`, `EventKind`, and query shapes wave 0 defined, and do not redefine them.

## What to build

- One SQLite database file, opened through the pure-Go driver `modernc.org/sqlite`, which is pre-approved in `docs/DEPENDENCIES.md`; add the `require` line and run `go mod tidy`. Open in write-ahead mode (`PRAGMA journal_mode=WAL`) with `synchronous=NORMAL`, a busy timeout, and one writer: writes go through a single connection guarded by a mutex, and reads may use others. The database file is the one `ARCHITECTURE.md` names, `~/.coeus/coeus.db`; the caller passes the path.
- One table of events: a sequence number that is the primary key and always increases, a timestamp, a task id, a kind, and the JSON body. Indexes for the read shapes below. The schema is created on open, with a `schema_version` table holding the number `1` so brief 6.3's migrations have somewhere to start.
- Write is one insert that returns the sequence number. Read is by task, by kind, by id, and by range of sequence numbers, each with a limit and each returning events in sequence order. A replay function hands a task's events back in order to a function the caller supplies, stopping on the first error, so that wave 3 can rebuild state after a crash and wave 6 can re-run a task as a test.
- Every operation takes a context and stops when it is cancelled. Every read has a cap on rows returned (the caller's limit, bounded by a package maximum), so nothing can load the whole log into memory by accident.
- Close flushes and closes. Opening a file that is not a Coeus log, or one with a newer schema version, returns an error that names the file and what to do.

## The borrowed designs

Read these two files to understand the design, then write it fresh in Go. Name both at the top of the file that ports each idea.

- Hermes' delivery ledger at `~/Code/hermes-agent/gateway/delivery_ledger.py`: the idea that the obligation is written before the action is taken, so a crash between the two leaves a record that says "this may have happened". Your log gives the caller the sequence number back so the caller can write the obligation first.
- OpenClaw's persisted queue at `~/Code/openclaw/src/infra/outbound/delivery-queue-storage.ts`: the idea of a durable queue on disk with a small, fixed set of read shapes and no clever indexing.

## Tests, in the order you write them

1. Unit tests for every read shape: by task, by kind, by id, by range, each with a normal case, an empty result, a limit smaller than the result, and a bad argument (a negative range, an unknown kind, an empty task id).
2. Ten thousand events appended and replayed in order, asserting every sequence number is exactly one more than the last and the bodies match.
3. The integration test (`//go:build integration`) opens the real file in a temporary home from `testkit`, writes, closes, reopens, and reads back; and it runs the crash test: a helper process (the test binary re-invoked with an environment flag, the standard Go pattern) writes events in a loop and is killed with `SIGKILL` mid-write; the parent reopens the file, runs `PRAGMA integrity_check`, and asserts every event it can read is whole and the sequence has no gaps.
4. A fuzz test on the event decoder: any bytes stored as a body decode either to an event or to an error, never a panic.
5. Concurrency: many goroutines appending at once all succeed and the sequence numbers are unique and dense.
