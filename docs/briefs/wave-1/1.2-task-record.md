## What to build

**The parser and the printer.** The record's text form is exactly the two examples in design section 4: the task record and the job record. Parse that text into the `contract` types (one set of types with a kind field, task or job) and print the types back to text, and the two must round-trip byte for byte on both golden files, saved under `testdata/`. The printer is the only thing that writes the text form; nothing hand-formats a record anywhere else in Nerd Genie.

**The job record.** The same four parts and the same rules, with these differences, each enforced in code: the header carries the progress line ("3 of 12 tasks done") and the next due task instead of the budget and cost lines; the work holds a task list instead of plan steps, each task with an id like `t31`, a check mark, a report id like `j4.2` once done, and a date when it must wait for one; the results are reports with ids `j<job>.<n>` and one-line summaries, full text in the log; tasks are listed in order; a task can be added or split but a finished task is never removed; a task marked done must name a report id. This package owns the job record's format and rules. Brief 4.4 owns the scheduler and the next-task rule and builds on this package.

**The rules, as code.** Every change to a record goes through a method that enforces these, and each rule has a named error that says which rule and what to do:

1. The ask, the why once set, and every correction are immutable after creation. A correction can only be appended, in the user's own words, with the next id (`C1`, `C2`, ...).
2. A decision must carry a reason; a failure must carry a cause. Ids are `D1`, `D2`, ... and `F1`, `F2`, ...
3. A plan step marked done must name a result id. A done line marked done must name a result id or a user reply.
4. Every result gets the next id (`r1`, `r2`, ...), one line in the record with a short summary, and its full text goes to the log through `contract.Store` the moment it arrives. `Read(id)` fetches the full text back from the log. This is the three-tier design the plan calls the fold tiers: the full text (in the window while there is room, or pinned), the one line (always in the record), the log copy (always, fetched by id). The record owns tiers two and three; the context builder of wave 2 owns tier one.
5. The record has four parts, goal, rules, work, and lessons, and the printer always prints them in that order with the goal and the rules first, because everything above the cache line must not move.
6. A record is created on the first tool call, with the task id, the origin channel, the ask, and the budget from configuration.
7. The header carries the budget line (rounds and minutes left) and the cost line (tokens in, cached, out for this turn). The harness updates both; the model never writes them.
8. The situation lines are written only by the harness.

**Checkpoints.** Every change saves a numbered checkpoint: the printed record goes to the log as a checkpoint event tied to the task, and the checkpoint number is returned. `Load(taskID)` reloads the latest checkpoint; `LoadCheckpoint(taskID, n)` reloads a specific one; `Back(taskID, k)` reloads the checkpoint k steps before the latest and saves it as a new checkpoint, which is what `/tasks 17 back 3` uses in wave 3.

**The size rule.** With a hundred-round budget the record cannot hold more than a hundred result lines, so a test fills it to the budget and asserts the printed text is under three thousand tokens by a simple count (whitespace-split words times a fixed ratio is fine; document the ratio).

**The done-check.** A function that reads the done list and returns the lines with nothing behind them. It does not run tools; brief 3.1 adds the mechanical checks on top. It must refuse to close a record while any done line lacks a result id or a user reply.

## Tests, in the order you write them

1. Round-trip on both golden records, the task and the job: parse, print, compare bytes; then parse the printed text again and compare structures.
2. One test per rule, for the task record and for the job record, each proving a bad edit is rejected with the named error and a good edit is accepted.
3. Every result readable by id after it left the record's memory, through the real log package in the integration test and through `testkit`'s fake store in unit tests.
4. Checkpoints: save, load latest, load by number, back by k, back past the first checkpoint is an error that says so.
5. The size test at the budget.
6. The forty-step fixture from `testkit`, driven without a loop: for each of the forty rounds, apply the scripted `task` operations and the scripted tool result to the record; append the correction during round twelve; assert the stop condition the record holds matches the round-thirty result; at the end run the fixture's three assertions (the ask and corrections are byte-for-byte what the fixture says, the done-check passes, every result id is readable). This is the first real run of the fixture and it must pass.
7. A fuzz test on the parser: any text parses to a record or an error, never a panic, and anything that parses re-prints and re-parses to the same structure.
