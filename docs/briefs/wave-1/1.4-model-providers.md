## What to build

Two implementations of `contract.Model`, one file each, plus the retry wrapper and the chain, all on the standard library's `net/http`, `encoding/json`, and `bufio`. No SDK: the plan says standard library first, and the fuzz test on the stream parser needs a parser you own.

**The Anthropic provider.** `POST {base}/v1/messages` with headers `x-api-key`, `anthropic-version: 2023-06-01`, and `content-type: application/json`; `stream: true` always. The system prompt goes in `system` as an array of text blocks; a block that ends a cache segment carries `cache_control: {"type": "ephemeral"}`. Tools go in `tools` as name, description, and `input_schema` (a JSON Schema object built from the spec's fields), and the last tool carries `cache_control` for boundary B; the boundary C block is the last system block that carries it. At most four blocks carry the marker. Messages: user text; assistant text plus `tool_use` blocks (id, name, input); user `tool_result` blocks (tool_use_id, content, is_error). Never send `temperature`, `top_p`, `top_k`, or `thinking`; Opus 4.8 rejects the sampling fields, and thinking is a deliberate wave-1 omission (a later wave may add it as one field once a real user needs it; do not add it now). `max_tokens` is the output cap from the request. Parse the event stream: `message_start` (usage in), `content_block_start` (text or `tool_use` with id and name), `content_block_delta` (`text_delta` and `input_json_delta`, whose partial JSON you accumulate per block index), `content_block_stop`, `message_delta` (stop_reason and usage out), `message_stop`, `ping`, and `error`. Map stop reasons: `end_turn` to end, `tool_use` to tool calls, `max_tokens` to length, `refusal` to stopped with the reason text. Usage: `input_tokens`, `output_tokens`, `cache_read_input_tokens` as cached, and `cache_creation_input_tokens` added to in. Errors: a 400 whose message says the prompt is too long, and a 413, are the overflow sentinel; a 429 is the rate-limit sentinel with the `retry-after` header parsed as seconds or as an HTTP date; 500, 502, 503, 504, and 529 are retryable; any other 4xx is returned as is with the body's message. The live model id is `claude-opus-4-8`.

**The OpenAI-compatible provider.** `POST {base}/chat/completions` (the base address already ends in `/v1`) with `Authorization: Bearer` when a key is set, `stream: true`, and `stream_options: {"include_usage": true}`. The system blocks are joined with blank lines into one `system` message; cache boundaries have no wire form here, because OpenAI and llama-server cache prefixes on their own. Tools go as `{"type": "function", "function": {name, description, parameters}}`; assistant messages carry `tool_calls` with `id`, `type: "function"`, and `function: {name, arguments}` where arguments is a JSON string; tool results are `tool` role messages with `tool_call_id`. The output cap is `max_completion_tokens` (the local daemon honors it, confirmed; OpenAI's reasoning models require it). Never send sampling fields. Parse `data:` lines: `choices[0].delta.content` for text, `choices[0].delta.tool_calls[]` accumulated by `index` (the id and name arrive on the first delta, the arguments in pieces), `choices[0].finish_reason` (`stop` to end, `tool_calls` to tool calls, `length` to length, `content_filter` to stopped), a final chunk with `usage` (`prompt_tokens`, `completion_tokens`, and `prompt_tokens_details.cached_tokens` as cached), and `data: [DONE]`. Errors: a 400 whose message matches the overflow phrases (`context_length_exceeded`, "exceeds the context window", "exceeds the available context size" from llama-server, "reduce the length of the messages", "maximum context length") is the overflow sentinel; read Prime's `overflow.ts` for the list and keep only what the three real servers say plus the generic fallback; 429 is rate-limited with `retry-after`; 5xx is retryable. The live model ids are `local-coder` on the daemon and `gpt-5.5` on OpenAI.

**The two local-model rules, adapted from Hermes.** When the base address is a loopback address, probe `GET {base without /v1}/props` once at construction with a two-second timeout. If it answers as llama-server does, send `chat_template_kwargs: {"enable_thinking": false}` in every request (the daemon bakes this in already; the field is belt and braces for other local servers) and, when the reported `default_generation_settings.n_ctx` is smaller than the configured context length, use the reported value and log one line saying so. If the probe fails, send nothing extra and use the configured length. Ollama is not probed and is not special-cased; it is the plain OpenAI-compatible path.

**Retries.** A wrapper around either provider: three attempts in all, backoff of one, two, and four seconds with a quarter of jitter, capped at thirty seconds, honoring `retry-after` when present; retry on rate limit, on retryable status codes, on connection errors, and on a stalled stream (no bytes for sixty seconds, a constant); never on overflow, and never on any other 4xx. Retries wait on `contract.Clock` so the tests use the fake clock. A retry is logged as one line. Read OpenCode's `retry.ts` for the shape of the delay function; write it fresh.

**The fallback chain.** A `contract.Model` built from an ordered list of models from the configuration: it tries the first, and when its retries are exhausted it moves to the next, and so on, returning the last error when all fail. Overflow is not a reason to move on: it goes straight back to the caller, because the context builder must fix the size. The reply reports which model answered.

**Streaming deltas.** Both providers call the delta callback for every piece of text as it arrives, in order, and the returned reply's text equals the concatenation of the deltas. Tool-call JSON is not streamed to the callback; it is complete in the reply.

**Bounds.** A request timeout on the whole call (from the request's deadline, default fifteen minutes from `contract`), the stall timeout above, a cap on the response body per event line, and a cap on accumulated tool-call JSON.

## Tests, in the order you write them

1. Against the fake provider server, for each API: a plain text reply streamed in deltas with the text equal to the concatenation; a reply with two streamed tool calls whose JSON arrives in pieces; the cache markers land where the request's boundaries say (assert on the recorded request body); usage counts come through; a stalled stream times out and is retried on the fake clock; a 429 with `retry-after` waits exactly that long; a 500 retries then succeeds; an overflow error returns the sentinel with no retry; a dropped connection mid-stream is an error that names the model.
2. The fallback chain moves on after exhausted retries and reports which model answered; it does not move on for overflow.
3. The llama-server probe: against a `testkit` server that answers `/props` with a smaller context, the smaller value wins; against one that does not answer, the configured value stands and no extra field is sent.
4. The contract test under `//go:build live`, one subtest per real model, and it fails loudly rather than skipping: the local daemon at `http://127.0.0.1:19091/v1` with model `local-coder` (fails with a clear message if `/health` is not ok); Anthropic with `claude-opus-4-8` using `ANTHROPIC_API_KEY` (a missing key is a failure that says which variable to set); OpenAI with `gpt-5.5` using `OPENAI_API_KEY` (same rule, and the test first lists `GET /v1/models` and fails naming the available ids if `gpt-5.5` is not among them). Each subtest sends a short prompt with one tool and asserts a text reply and a tool call both work, and it prints the usage so the orchestrator can record the cost in `docs/PROGRESS.md`.
5. A fuzz test on each stream parser: any bytes produce a reply or an error, never a panic, and never a hang past the stall timeout on the fake clock.
