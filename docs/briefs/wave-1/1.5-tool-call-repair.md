## The package

`internal/repair`. One sentence: find the tool calls in a model reply, however the model wrote them. Design section 3, rule 5 ("A badly formed tool call is repaired if the tool name is close to a real tool's name. Otherwise the model gets back the list of real tools. Text that merely looks like a tool call is read as one. The agent loop never crashes because of something the model wrote.") and `COEUS.md` section 7 (small models write their tool calls badly). The plan text is `docs/WORK_PLAN.md`, Part 3, Brief 1.5. The tool call type and the tool names are in `internal/contract`.

## What to build

One function is the whole package: it takes the reply (the structured tool calls the provider already parsed, if any, plus the raw text) and the list of real tool specs, and returns the tool calls found, the text that remains once the tool-call envelopes are removed, and, when something looked like a call but could not be repaired, an error message written for the model that names the real tools. It never panics and never returns both an error and calls.

The envelope shapes it must read, in this order of trust:

1. Structured tool calls from the provider: passed through, with only the name check below.
2. A `<tool_call>` block (with or without a closing tag, one or many) holding JSON with `name` and `arguments` or `input`.
3. JSON in a code fence, ` ```json ` or bare ` ``` `, holding one object or an array of objects with a name and arguments.
4. A bare JSON object in the text with a `name` field and an `arguments` or `input` object.
5. A function-call line of the form `name({...})` or `name: {...}`.

Name repair: an exact match wins; then a case-insensitive match; then a match ignoring underscores and hyphens; then an edit distance of at most two against the real names when the candidate is at least five characters. A repaired name is reported so the loop can log it. A name that matches nothing produces the error naming the real tools.

Arguments: the JSON must decode to an object; a string that itself holds JSON is decoded once more; anything else is an error naming the tool and the shape it expects, taken from the spec's fields.

The two-failures rule: the function takes the number of consecutive failed parses so far. After two failures in a row, text that still looks like a call is returned as the answer with no error, so the loop stops fighting the model. The loop of wave 3 keeps the counter; this package only applies the rule.

Bounds: the text is capped (a constant, and anything past it is not searched); the number of calls found is capped at the same limit as the identical-call window in `contract`; regular expressions are compiled once.

## Tests, in the order you write them

1. A golden file per envelope shape under `testdata/`: the input text and the expected calls, remaining text, and error, compared with the `testkit` golden helper. Include the shapes small models actually produce: a call followed by prose, prose followed by a call, two calls in one reply, a fence with a language tag, a `<tool_call>` block with no closing tag, arguments as a JSON string.
2. Name repair: each rule in the order above, and a name that is close to two real names picks the closer one or, on a tie, errors.
3. The two-failures rule: a bad call with zero and one prior failures errors; with two it is the answer.
4. Bounds: text past the cap is not searched; more calls than the cap are truncated with a note in the error.
5. A fuzz test: any text with any set of tool names never panics, and anything returned as a call re-encodes to valid JSON.
