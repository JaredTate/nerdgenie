# Brief 2.1: the working context builder

Before you write anything, read these five files in this order: `CLAUDE.md` for the rules and the commands, `COEUS.md` for the plain-words explanation of the state design and the check table that ties each claim to a brief and a test, `ARCHITECTURE.md` for how the code is put together and what earlier waves built, `REPO_MAP.md` for where everything lives, and `docs/NERDGENIE_PLAN.md` for the design you are implementing, especially the section this brief names. Then read this brief and the reference files it points at. You own exactly one package. Write the tests first.

## The package

`internal/context`. One sentence: build the working context from the layers, sized to the model. Design section 4, "Working context: one rule, sized to the model" (the layer table, the three cache points, what leaves the window, the cost line, the proof), section 5 (the instruction text, which is a constant here), and `COEUS.md` sections 7 and 8. The plan text is `docs/WORK_PLAN.md`, Part 3, Brief 2.1. You build on `internal/contract`, `internal/record` (the printer, the result reader, the cost line setter), and the request type the provider consumes. You may import `internal/provider` only in the live test.

## What to build

- **The instruction text.** The full text of design section 5 as a constant, byte for byte from the design, and a test that counts its words and asserts under five hundred. When the design's text changes, the constant changes with it and the test still holds.
- **The layers, in order, each a separate system block in the `contract` request:** the instruction text and the persona (the three files `SOUL.md`, `USER.md`, `MEMORY.md` from the home folder, each read once per build, each capped at its `contract` size and cut with a note if over) ending with cache boundary A; the tools, which the provider renders, ending with boundary B; the job summary when the task belongs to a job (the job record's goal, rules, and task list, printed by `record`); the record's goal and rules, ending with boundary C; then, below the cache line, the record's work and lessons; pinned evidence, word for word; the recent messages and tool results; and the memory hint, three lines from `contract.Memory` for the current step. Below the cache line goes into the messages, not the system blocks, so nothing above the line moves.
- **The one rule.** The window is the model's context length minus the output cap minus the size of everything above the cache line minus the record's live part. Results fill the window newest first, in full. When the window is full, the oldest result's full text leaves; its line in the record and its copy in the log stay, and `read r7` brings it back. Pinned evidence never leaves; if pins alone overflow the window, the build returns an error naming the pin to drop. Token counts are an estimate from a fixed ratio of characters to tokens, documented in one place, and a test shows the estimate is within twenty percent of the fake provider's reported input count on the fixture.
- **Nothing above the cache line changes during a task.** The build is deterministic: the same inputs produce the same bytes, and the blocks above boundary C are byte-identical from one turn to the next unless the persona files, the tools, the job, or the record's goal and rules actually changed.
- **The cost line.** After each call the caller hands the provider's usage to this package, and it writes the record header's cost line through `record`: tokens in, of which cached, and out, in the design's format ("this turn: 6.1k tokens in, 5.2k of them cached, 0.4k out").
- **Tool results as data.** Every tool result placed in the messages is wrapped in the data marker the design describes (section 3, rule 8), with a random per-task boundary id, so words inside it are never read as instructions. The marker text is a constant here and the loop of wave 3 relies on it.

## What not to build

No summarizing, ever. No compaction. No provider-specific formatting; the provider owns the wire. No reading of skills; the skill bodies of wave 4 arrive as a block the caller passes in.

## Tests, in the order you write them

1. The word count of the instruction text.
2. A golden prompt for a 24k model and one for a 200k model, built from the forty-step fixture at round twenty, compared with the `testkit` golden helper; the two share every byte above the cache line and differ only in how many results are in the window.
3. Nothing above the cache line changes across ten turns of the fixture.
4. Every result that has left the window is still readable by id through `record`.
5. The cost line matches the fake provider's counts after a call through the fake model.
6. Pins never leave; pins that overflow return the named error.
7. The persona files: missing files are fine, oversized ones are cut with a note.
8. The data marker wraps every tool result and the boundary id differs per task.
9. Under `//go:build live`: the same fixture task on all three real models produces a prompt within each model's window, sent through `internal/provider`, and the reply's usage is printed for `docs/PROGRESS.md`; a missing key or a daemon that is down fails loudly.
10. A fuzz test on the persona file reader and the size estimator: any bytes, no panic.
