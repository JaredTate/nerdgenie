## What to build

- **Rules.** A rule is a tool name or `*`, a pattern, and an action: allow, ask, or deny. Patterns are globs matched against the call's reduced form (below). The rules come from the configuration's ask-me-first list, which ships with three entries and which the user may change or empty; the harness adds no rule the user cannot see. Evaluation: last match wins; no match means allow. The three shipped entries, each a set of patterns with a plain name: bulk or recursive deletes (`rm -r`, `rm -rf`, `rm -fr`, `find ... -delete`, `git clean -f`, `git reset --hard`, and a `write` or `edit` that empties a file over a size, and the `browser_act` and `computer` intents that say delete all), sudo (any `shell` call with the escalate field set), and spending money (`browser_click`, `browser_act`, and `computer` calls whose intent or target text contains buy, pay, purchase, checkout, subscribe, or order, and any `web` fetch of a URL with those words in its path). Write these as data in one file with a test each.
- **The reduced form.** A shell command is reduced to a readable prefix the way OpenCode's arity table does it: the program and the subcommand words that matter, without arguments that vary (`git commit -m "..."` becomes `git commit`; `rm -rf /tmp/x` becomes `rm -rf`). Other tools reduce to the tool name plus their main field (the path, the URL, the intent). The reduced form is what the pattern matches, what the log records, and what the preview shows.
- **The verdict.** Allow, ask, or deny, with the reason (which rule matched, or "no rule") and, for ask, the preview text: exactly what is about to happen, in plain words, the same way you read a text back before you hit send. For a shell command the preview is the full command; for a write it is the path and the size; for a browser action it is the intent and the element.
- **Remembered answers.** Once (this call only), always (for the session, keyed by the reduced form), reject with a reason (this call is denied and the reason goes back to the model). A session's remembered answers live in memory and are gone on restart; the plan adds nothing durable here.
- **Standing approvals for skills.** A skill may carry a standing approval: a reduced form, a limit on uses, and an expiry. The loop of wave 4 registers them; you store and check them: a matching call is allowed until the limit or the expiry, and an expired one asks again.
- **Unattended runs.** A call carries an unattended flag (a scheduled task, no user present). When the verdict is ask and the run is unattended, the function returns a distinct stop verdict with the preview text, so the loop stops the task and reports instead of waiting forever.
- **Bounds.** Rule lists are capped; patterns are compiled once; a pattern that fails to compile is a configuration error that names it.

## Tests, in the order you write them

1. A table of rules and calls covering allow, ask, deny, last match wins, and no match.
2. Prefix reduction on twenty commands, including quoted arguments, pipes, `sudo` prefixes, and env assignments.
3. Each of the three default entries: the calls that must ask and near misses that must not.
4. An empty list allows everything.
5. Remembered answers: once does not stick, always sticks for the session, reject returns the reason.
6. A standing approval within its limit allows, then asks after the limit, and an expired one asks.
7. An unattended run that hits the list returns the stop verdict with the preview.
8. A fuzz test on the pattern matcher and the reducer: any input, no panic, and the reducer's output never contains a newline.
