## The package

`internal/tool`, with one folder per tool under it (`internal/tool/read`, `internal/tool/write`, and so on), each a package with one job, and the registry in `internal/tool` itself. Design sections 6 ("Tools": the five parts, the user's own tools, the permission class) and 7 (the eighteen tools and their classes, results built by the harness), and `COEUS.md` section 13. ## The registry

- Loads the built-in tools and every executable in `~/.coeus/tools/` through the user-tool protocol in `contract`: run it with `--describe`, parse the JSON spec, and register a tool that runs the executable with the input JSON on standard input and returns its standard output, under the tool timeout, in its own process group. A user tool whose spec fails to parse is skipped with one logged line naming the file and the problem.
- Rejects any description over forty words, built-in or user, at registration, with an error naming the tool.
- Applies the output cap from the configuration to every result: text past the cap is written to a file under `~/.coeus/run/spill/` named by task and result, and the result ends with one line naming that file, so the model can `read` it.
- Renders the spec list in the shape the model request needs, and looks a tool up by name for the loop.
- Marks every result as data: it never interprets the text, and the context builder wraps it.
- Bounds: the number of tools, the spill folder size (oldest files removed past a cap), and the description length.

## The eighteen tools

Each folder has its own `doc.go`, a description under forty words that says when not to use the tool, typed fields, the permission class from design section 7, tests against the fakes, and a golden result file under `testdata/`. In the list, "thin" means the tool validates its input, calls one method on the contract, and returns the text.

1. `read` (R): a file (with line numbers, a byte cap, and an offset and limit), a directory listing, or `read r7` for a past result through `record`, and `read j4.2` for a job report. A binary file is refused with a note. Paths are limited to the sandbox roots.
2. `write` (W): creates or overwrites a file inside the roots; refuses a path outside them; saves the file's prior contents (or the fact that it did not exist) to the event log as a file-change event whose body is `contract.FileChangeBody`, before writing, so `/undo` in wave 3 can restore it.
3. `edit` (W): replaces one exact span; when the exact text is not found, tries the fallback matchers in order (trimmed lines, whitespace-normalized, indentation-flexible, a unique substring), refuses when the match is not unique, and saves the prior contents to the log the same way `write` does.
4. `search` (R): files by name pattern, or lines by regular expression, through `rg` when present and a slow Go fallback when not, fifty rows at most, limited to the roots.
5. `shell` (X): runs a command through `contract.Sandbox` in its own process group; returns after ten seconds with a process id when the command is still running, and offers `poll`, `tail`, and `kill` on that id through an `action` field, with a bounded table of running processes; an `escalate` field with a written reason asks `contract.Permission` for a preview and, once approved, runs the command outside the sandbox with `sudo -A` and `SUDO_ASKPASS` set to the coeus binary's askpass subcommand (brief 2.4 provides it; you take the path from the configuration); refuses to run at all when the sandbox reports unavailable, with a message that says why.
6. `web` (N): `search` through the configured SearXNG address as JSON, or, when none is configured, by fetching the DuckDuckGo HTML results page and reading it as text; and `fetch` of a public page as text with a pinned DNS lookup (resolve once, connect to that address, refuse private and loopback ranges, and refuse a redirect to one), a size cap, an HTML-to-text step that keeps headings, links, and list structure, and the external-content wrapper with a random per-call boundary id. The fake search server and the fixture pages in `testkit` are the test doubles.
7. `memory` (R and W): thin over `contract.Memory`: search, get, save.
8. `skill` (R, X, and W): thin over `contract.Skill`: view, run, save.
9. `job` (I): thin over `contract.Job`: create a job with or without a schedule, add a task to it, list its tasks.
10. `task` (W): the only way the model writes the record, through `record`: set the why, the done list, the stop list, the plan, add a decision with its reason, add a failure with its cause, or pin a result. Each operation goes through `record`'s rules, and a refused operation returns the rule's message so the model can fix it. It rides in the same reply as other tool calls, so it must be cheap and never block.
11. `browser_open`, 12. `browser_read`, 13. `browser_click`, 14. `browser_type`, 15. `browser_act` (N and X): thin over `contract.BrowserWorker`, each returning the snapshot or diff as text the model reads.
16. `browser_login` (N and I): takes a site name, calls the worker's `loginFill` with credentials the harness supplies through a function the caller injects (wave 5 wires the vault); the tool never sees or returns a value.
17. `browser_handoff` (N and I): thin over the worker's handoff, returning what the user replied.
18. `computer` (X and I): thin over `contract.Desktop`.

## Tests, in the order you write them

1. A user tool (a shell script the test writes) registers and runs end to end; one with a broken spec is skipped with the logged line.
2. A long description is rejected.
3. Overflow spills to a file and the result names it.
4. A golden result per tool.
5. Every `edit` fallback, and the refusal when a match is not unique.
6. A `write` and an `edit` outside the roots are refused; the prior contents are in the fake log after each.
7. A one-second shell command returns its output; a thirty-second one returns a process id at ten seconds, then `poll`, `tail`, and `kill` work on the fake clock where the sandbox is the fake and on the real sandbox under `integration`.
8. An escalation that previews through the fake permission and does not run until approved; approved, it runs with `sudo -A` (asserted through a fake `sudo` on the PATH that records its arguments).
9. A fetch of a fixture page produces the expected text with the wrapper; the page that contains instructions changes nothing in the result but the text.
10. A search with no server configured goes to the fake DuckDuckGo page and returns rows; with a server configured it goes to the fake SearXNG.
11. A private-address redirect is refused; a loopback target is refused unless it is the configured test server.
12. Every `task` operation against the record rules, good and bad.
13. The thin tools round-trip through their fakes.
14. Fuzz tests on the edit matcher, the shell command parser, and the HTML-to-text step: any input, no panic, bounded output.
