## What to build

**One task at a time.** A `Loop` takes a task (an inbound message with its channel, or a `contract.TaskToRun` from a job) and runs it to an end state: done, waiting on the user, stopped, or failed. A second task waits in a queue the caller drains; the loop itself never runs two tasks at once, and a test proves the second waits. When nothing is running, the caller asks `contract.Job` for the next due task and runs it through the same path with the unattended flag set.

**The turn.** For each round: build the working context through `context` (which reads the record and the job summary when the task belongs to a job); call the model with deltas forwarded to the channel; read the reply through `repair` (every reply goes through it, so a `cli` model's text calls and a small model's loose calls become calls the same way); orient (the reply's first line is the model's statement of where it stands, logged and written into the record's situation as the last orient line); guard; permit; run; update the record; repeat. A reply with no tool calls ends the turn. The harness tells a question from an answer by the finish state and a trailing question mark on the last non-empty line; a question puts the record into the waiting state and the next message from the user resumes it, even days later, from the last checkpoint.

**The guard, in order.** (1) The stop list: before any tool call, every line of the record's stop list, plus the two harness lines (the budget running out; a login page, a two-factor prompt, or a captcha reported by a browser tool result), is checked against what the harness can see, and a hit stops the task and tells the user which line. (2) The budget: one hundred rounds and one hour by default from `contract`, which a skill may override through a field on the task; when it runs out, one last call with tools off asks for the report of what was done and what is left. (3) The identical-call detector: the same tool with the same arguments, across the last twenty calls of the task (the window from `contract`) and inside one reply, is not run; the model is told to do something different or to answer, and a third identical call ends the turn. (4) Malformed calls: a call `repair` could not fix goes back as the error naming the real tools; after two failed parses in a row the text is the answer.

**Permit.** Every call goes to `contract.Permission` with the reduced request. Allow runs it. Ask shows the decision's preview through the channel and remembers the answer (once, always, reject with a reason to the model). An unattended run that gets the stop verdict ends the task with a report of what needed an answer. Every ruling is logged as a permission-decision event.

**Run.** Each tool runs under the tool timeout from `contract`, and the result goes through `record` (one line in the record with the next result id, the full text to the log) and into the working context as data. A tool that fails returns its error to the model with the three options from design rule 6 appended: answer the user, ask one question, or try different arguments.

**Mid-turn messages.** A message from the user that arrives during a task is queued and, as soon as the current tool call finishes, shown to the model with the record; the model writes it as a correction through the `task` tool (the harness copies the user's words into the record first, word for word, so the correction is there even if the model does nothing), handles it as a new request and then resumes, or stops when it says stop. Words that mean stop are a short fixed list.

**The situation.** The harness fills the record's situation lines from what it can check: the browser tab and page title from the last browser result, the files changed in this task from the file-change events, the last command and its exit code from the last shell result, and the last orient line. No model call.

**The done-check.** When the model says the task is done, run `record`'s done-check; a done line with nothing behind it sends the model back to work with one line naming the rule. For a line that names a file path, check the file exists; for a line that names a command in backticks, run it through the sandbox tool and check it exits zero; otherwise the model must name the result. A task cannot close until every line passes.

**The review.** When the task had a correction, a failure, a stop, or more than five rounds, ask the four questions in one call with tools off, one line each: what was supposed to happen, what happened, why they differ, what to keep or change. Save only the fourth answer: as a fact through `contract.Memory` with the task as its source, and, when it describes a procedure (a fixed list of verbs at the start of the line: "to do X, first...", "the steps are"), offer it to `contract.Skill` through the channel as a preview the user can approve.

**Reports.** A finished task sends the short report through its channel: what changed, what was checked, what is left. A stopped or failed task sends what happened and, for a stop, which line fired. When the task belongs to a job, the report goes into the job through `FinishTask` and the message to the user carries the job's progress line; when the job's last task finishes, run the job's done-check and review the same way and send the final report.

**Commands.** Export `/tasks` (list running, waiting, and done tasks; `/tasks 17` prints the record; `/tasks 17 back 3` rewinds three checkpoints through `record`) and `/stop` (stop the running task) as `contract.Command` values; the orchestrator registers them.

**Bounds.** Every wait has the deadline from `contract`; the queue of mid-turn messages is capped; the orient line is capped in length; the number of tool calls per reply is capped at the identical-call window.

## Tests, in the order you write them

Every test drives the loop with the fakes from `testkit`: the scripted model, the fake registry with scripted tools, the fake permission, the fake channel, the fake job, the fake clock, the fake store, and a real `record`.

1. A scripted conversation per rule of design section 3, ten tests, each named for the rule.
2. A task in a job reports to the job and starts the next; the last task closes the job with its own done-check and the final report through the fake channel.
3. The detector across steps and inside one reply; the third identical call ends the turn.
4. The budget: the hundred-and-first round gets the tools-off call and the report; the one-hour limit on the fake clock does the same.
5. A mid-turn correction lands in the record word for word; a mid-turn new request is answered and the task resumes; a mid-turn stop stops.
6. A question ends the turn waiting; the next message resumes from the checkpoint with the record intact.
7. A done-check that fails on a line with no evidence sends the model back; a line naming a file passes when the file exists; a line naming a command passes when it exits zero.
8. The review runs only when it should (four tests: correction, failure, stop, more than five rounds; and one that shows it does not run otherwise); the fourth answer lands in the fake memory; a procedure answer produces a skill offer through the fake channel.
9. A finished task and a failed task each produce the right message through the fake channel; an unattended task that hits the ask-me-first list stops and reports.
10. The forty-step fixture end to end against the fake model: the three assertions pass.
11. A fuzz test on the reply handler: any reply text and any set of tool calls never panic and never hang past the deadline on the fake clock.
