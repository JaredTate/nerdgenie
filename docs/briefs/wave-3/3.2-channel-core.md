## What to build

- **The queue.** Every inbound message from every channel goes into one queue in the SQLite file before anything looks at it, capped at the configured number of queued messages (a full queue refuses with a message the channel sends back). The loop's caller drains it in order. A message survives a restart: it is marked taken when handed out and done when the task that it started ends, so a crash between the two hands it out again with the duplicate marker set.
- **The router.** For each message: a text that starts with `/` is a command, looked up through a function the orchestrator supplies (`func(name string) (contract.Command, bool)`) and run with the channel it came from; otherwise `contract.Skill.Match` is asked, and a match runs the skill without the model; otherwise the message is a task for the loop. The router hands each kind to a function the orchestrator supplies for it, so this package knows nothing about the loop.
- **The event stream.** One stream of events from the loop (deltas, replies, previews, questions, handoffs, status, errors, in the `contract` socket envelope shape) that every attached channel subscribes to; a slow subscriber is dropped after a bounded backlog rather than stalling the others.
- **The socket.** A Unix socket at the home's socket path, mode `0600`, speaking one JSON envelope per line both ways as `contract` defines. A client sends `attach` and then receives the stream; `message` and `command` go into the queue; `approve`, `deny`, and `secret` answer the pending preview or masked prompt by id; `detach` stops the stream. Several clients may attach at once. The socket is a `contract.Channel` named `terminal`: it receives, sends, sends a file (the path in the envelope's attachments), shows a preview (sends `preview` and waits for `approve` or `deny` with a deadline), asks a secret (sends `ask` with the secret flag and waits for `secret`), and reports health. Every outbound text goes through `contract.Secrets.Redact` before it is written.
- **Bounds.** Line length on the socket is capped; a client that sends a bad line gets one `error` envelope and is disconnected; attached clients are capped; the preview wait has the deadline from `contract`.

## Tests, in the order you write them

1. Two fake channels subscribed to the stream receive the same events in the same order; a slow one is dropped after the backlog cap and the fast one is unaffected.
2. A queued message survives a restart: queue, take, close, reopen, and the message is handed out again with the duplicate marker.
3. The router sends a command, a skill trigger, and a task each to the right function, using the fake skill store and a fake command lookup; an unknown command answers with one line naming `/help`.
4. A client attaches over the socket, sends a message, and streams a reply delta by delta; two clients see the same stream.
5. A preview round-trip over the socket with approve, with deny, and with a timeout.
6. A masked-prompt round-trip returns the secret and never writes it to the log.
7. A bad line disconnects the client with an error envelope; a line past the cap does the same.
8. The socket passes `testkit`'s channel contract check.
9. The integration test (`//go:build integration`) runs the queue on the real database in a temporary home.
10. A fuzz test on the socket line reader: any bytes, no panic, always an envelope or a disconnect.
