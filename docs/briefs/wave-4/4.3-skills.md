## What to build

- **The folder format.** `SKILL.md` with the name, a one-line description, the trigger words, and a permissions block (the browser profile, the sites it may visit, its daily limit, and which steps cannot be undone); `steps.md` (a numbered list of steps, each a tool call with its intent and what to expect) or `script` (an executable); `test.md` (a dry run that runs to the first irreversible step and stops); `CHANGELOG.md` (every change with a way to undo it). A loader that validates the folder and refuses a step over a size limit or a missing file, with an error naming the file.
- **The prompt line.** `List` returns names and one-liners only; `Load` returns the body when the skill is used.
- **The permissions block, enforced.** When a skill runs, its permissions become standing approvals in `permission` with the daily limit and an expiry at midnight, and a step outside the block asks the user.
- **The changelog with rollback.** Every save appends an entry with the previous version stored beside it; `/skills rollback <name>` restores it.
- **The trigger matcher.** `Match` compares a message's words against every skill's trigger words and returns the one skill that matches all of its triggers, or nothing; the router calls it before the model.
- **Replay.** `Run` executes the steps through the tool registry with no model call, checking each step's expectation; on a failed step it returns what failed and what was seen, and the loop decides whether to call the model.
- **Learning.** From documentation: given a page's text, write a skill folder with the commands the skill will use and one example each, run the dry run, and save it when it passes. From a task: given a finished task's record, offer to save its steps as a skill through the channel; approval saves a valid folder. From the review: a fourth answer that describes a procedure is offered the same way. The offers go through a function `serve.go` wires to the channel.
- **`/skills`.** A `contract.Command`: list, show one, run one, rollback one, remove one (which keeps the folder under a `removed` name).
- **Bounds.** The number of skills, the size of a step, the number of steps, the daily limit.

## Tests, in the order you write them

1. A golden folder under `testdata/` loads; a folder with a missing file or an over-limit step is refused with the file named.
2. Rollback restores the previous version and the changelog records both.
3. A trigger runs a skill through the fake registry with the fake model never called.
4. A scripted page produces a skill that passes its dry run.
5. A completed task's record produces an offer through the fake channel, and approval saves a valid folder.
6. The permissions block becomes standing approvals in a real `permission` instance, and a step outside the block asks.
7. The contract check from `testkit` passes.
8. A fuzz test on the `SKILL.md` parser: any bytes, no panic.
