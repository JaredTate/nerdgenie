## What to build

- **The process.** `node worker/browser/dist/main.js --profile <folder> [--chrome <path>] [--pacing human|fast]`. It launches the Chrome binary named by `--chrome`, or `google-chrome` from the PATH, with `--user-data-dir=<profile>` (never the user's daily profile), `--remote-debugging-port=0` on the loopback address, and a fresh per-launch token in the DevTools address, reads the port Chrome prints, attaches with `chromium.connectOverCDP`, and then reads JSON-RPC requests one per line from standard input and writes one response per line to standard output. Nothing but responses goes to standard output; logging goes to standard error, one line per event, plain English. `--pacing fast` exists only for the tests, which cannot wait for human pacing; the Go side never passes it.
- **Snapshots.** Build the compact tree from Playwright's accessibility snapshot and the DOM: every link, button, text box, checkbox, combobox, menu item, heading, and article that is visible or scrollable into view, each with a ref (`e` and a number, stable for the element while it exists on the page), its role, its accessible name, and `new: true` when it was not in the previous snapshot. Count what is below the fold. Report an open dialog and a started download. Cap the element list at a few hundred entries and say so in `belowFold` when the cap cut it. Never include the page's markup or scripts.
- **Actions.** `click`, `type`, `press`, `scroll`, and `act` as the protocol says: find the element by ref; when the ref is stale, by role and name; then by visible text; scroll it into view; wait until it is visible, enabled, and stable; act with pacing (a mouse move along a curve, a click held for a human length of time, one key at a time with small random gaps, scrolling in steps, a pause between actions); wait for the page to settle (a navigation finished, or no DOM mutation for three hundred milliseconds, limit three seconds, then error -32001); take the new snapshot; build the diff. A click with no visible change is retried once at the element's screen position before reporting.
- **Expectations.** The worker cannot judge English, so the rule is fixed and tested: split the expectation into words of four or more letters that are not stop words; the expectation is met when any of them appears in a new element's name or role, in the new address, in the new title, or in a dialog's message, or when the expectation is empty and something changed. Otherwise `expectationMet` is false and `seen` says in one sentence what did change ("the address changed to ...", "two new buttons appeared: ...", "nothing changed").
- **Walls.** After every action and every `open`, look for a login form (a password field, or a form whose name or heading says sign in or log in), a second-factor prompt (a field or heading that says code, verification, or authenticator, with a short numeric input), or a captcha (an element, frame, or heading that says captcha, hCaptcha, reCAPTCHA, or "verify you are human"). The fixture list of roles and text lives in one file with a test per entry. A wall fills `wall` in the diff and sets `expectationMet` false; the worker never tries to get past it.
- **`loginFill`.** Types the username, password, and code into the refs given, with pacing, then presses Enter in the last field it filled, settles, and returns a diff in which every occurrence of the three values, in any field of the snapshot or the diff, is replaced by `[redacted]` before the object is built. A test greps the whole JSON response for the values and finds none.
- **`tabs`, `screenshot`, `health`.** As the protocol says. The screenshot numbers the clickable elements with drawn marks and returns the mark list. Health returns the Chrome version it attached to.
- **Everything a human can do.** Popups and new tabs are tracked as tabs; frames are walked for the snapshot; dialogs are reported, never auto-accepted; downloads are saved under the profile folder's `downloads/` and reported; PDF pages are read as text through Chrome's viewer where possible and otherwise reported as a download.
- **Bounds.** Every method has a deadline (a constant per method); a snapshot is capped; a `type` text is capped; an `act` batch is capped at ten steps; standard input lines are capped in length and a longer one is answered with -32700.
- **Build.** `package.json` with `playwright-core`, `typescript`, `vitest`, and `fast-check` as the only dependencies, pinned; `tsconfig.json` strict; `npm run build` produces `dist/`; `npm test` runs Vitest with coverage and fails under seventy percent. Add the four packages to `docs/DEPENDENCIES.md` with one line each; they are pre-approved by this brief. The `Makefile`'s `build` target will bundle `dist/` in wave 5; leave the Makefile alone.

## Tests, in the order you write them

Tests run against recorded fixture pages under `worker/browser/test/pages/`, served by a tiny static server the tests start on a loopback port: a page with links, buttons, and a form; a page that changes after a click; a page with a dialog; a page with a download link; a page that opens a new tab; a page with a frame; a very long page; a login page; a two-factor page; a captcha page. They run Chrome for real with `--pacing fast` and a temporary profile, on the development machine's display; the CI workflow will run them under `xvfb-run` when wave 5 wires it, so keep every test free of assumptions about the screen size.

1. The wire: a good request, a non-JSON line (-32700), an invalid request (-32600), an unknown method (-32601), wrong parameters (-32602), each with a golden response.
2. Every method against the fixture pages, one test each, with the response compared field by field to what the protocol's examples promise.
3. A stale ref re-found by role and name, then by text; a ref that is gone everywhere returns -32000 with a fresh snapshot in `data`.
4. A click with no change is retried once at the screen position, then reported with `expectationMet` false and `seen` saying nothing changed.
5. A settle timeout on a page that never stops mutating returns -32001.
6. A dialog is reported and not accepted; a download is saved and reported; a new tab appears in `tabs`.
7. A large page stays under the snapshot cap and `belowFold` says so.
8. The wall detector on the login, two-factor, and captcha fixtures, and no wall on the ordinary pages.
9. `loginFill` never returns a value: the whole response is searched.
10. The expectation rule: a table of expectations against diffs.
11. Property tests with `fast-check`: any string as an expectation never throws; any bytes on standard input produce a response or -32700 and never crash the process; any sequence of refs never throws.
12. Pacing: in `human` mode, the gaps between keystrokes vary and the mouse path has more than two points; in `fast` mode the whole suite runs in under two minutes.

## Definition of done

- Every method in `PROTOCOL.md` implemented and tested; the process never writes anything but responses to standard output.
- Coverage above seventy percent under `npm test`; `npm run build` clean under strict TypeScript; no file over five hundred lines; no function over sixty lines.
- Plain English in every identifier, comment, and log line.
- `docs/DEPENDENCIES.md` lists the four packages; `ARCHITECTURE.md` has a short `worker/browser` paragraph saying what exists; `REPO_MAP.md` is regenerated with `make repo-map` if the Makefile exists on your branch, and otherwise you say so in your report.
- Tests first, in the git history: the failing test committed before the code that makes it pass, for every piece.
