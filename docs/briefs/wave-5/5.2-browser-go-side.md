## The package

`internal/browser`. One sentence: the Go side of the browser, which starts and supervises the worker, paces it, logs in from the vault, and hands the window to the user. Design section 9 in full and section 11, "The vault" (the model never sees a secret; `browser_login` types it). The plan text is `docs/WORK_PLAN.md`, Part 3, Brief 5.2. ## What to build

- **The worker client.** A `contract.BrowserWorker` implementation that speaks `worker/browser/PROTOCOL.md` over the standard input and output of a child process: one request at a time, a deadline per method, one JSON object per line, errors mapped to Go errors that carry the code and the fresh snapshot when the protocol says so. The process is started with the profile folder from the configuration (mode `0700`, outside the sandbox) on the first browser tool call, kept alive for thirty minutes after the last call, restarted with backoff when it dies, and the interruption is reported to the model as the protocol's error table says. Kill only by exact process id.
- **Pacing and the budget.** A pacing profile (human by default) passed to the worker, and a per-site daily budget of actions from the configuration, counted per hostname per day on `contract.Clock`; a call past the budget is refused with a message that says the number and when it resets.
- **Login.** `Login(site)` finds the vault entry through `contract.Secrets.Resolve`, checks the current page's hostname is one of the entry's domains (refusing otherwise with the hostname named), takes the refs of the username, password, and code fields from the current snapshot (by role and name, or the refs the model passed), makes a fresh TOTP code through `vault` when the entry has a secret, waiting for a fresh window when fewer than five seconds remain, calls `loginFill`, and reports success or the wall it hit. Nothing from the credential is ever logged or returned.
- **Handoff.** `Handoff(reason)` brings the window forward (through the worker), takes a screenshot with numbered marks, sends it through the current channel with a numbered list of what the person can do (reply `done`, reply a code, reply `abort`), blocks the task until the reply arrives or the configured handoff timeout passes, and returns the reply. A code reply is typed into the field the wall named.
- **`/screen`.** A `contract.Command` that sends a screenshot of the browser now through the channel it was typed on.
- **Bounds.** The method deadlines, the restart backoff cap, the daily budget, the handoff timeout, the screenshot size cap.

## Tests, in the order you write them

1. The worker is spawned once and reused across calls; after thirty idle minutes on the fake clock it is stopped; a dead worker is restarted with the interruption reported.
2. Every protocol method round-trips through the fake worker's JSON-RPC server, including each error code.
3. The daily budget refuses at the limit and says when it resets.
4. A login on the fake login page succeeds with a TOTP code from a known secret; a wrong domain is refused; the response never holds a value (the whole JSON is searched).
5. A handoff round-trip through the fake channel with `done`, a code, and `abort`; a handoff that times out.
6. `/screen` sends a picture through the fake channel.
7. Under `integration`: the real worker from `worker/browser/` starts against a temporary profile, answers `health`, opens a fixture page served on a loopback port, and is stopped by exact process id.
8. A fuzz test on the protocol line reader: any bytes, no panic.
