## What to build

- **Recording.** While the user drives the agent's own Chrome window, or while the agent completes a browser task, record each step's intent (what the step is for, in words), its element descriptor (the ref, the role and name, and the visible text, so the element can be found three ways later), and its expectation (what the diff should show). The recording becomes a `steps.md` in a skill folder through `internal/skill`.
- **Replay.** Run the recorded steps through the worker with no model call: find the element through the cascade (ref, then role and name, then text), act with the recorded expectation, and stop at the first unmet expectation with what was seen.
- **Self-heal.** When a step fails on replay, ask the model (through `contract.Model`, one call with the intent and the current snapshot) which element matches the intent, verify by acting with the expectation, and, when it works, propose a one-line patch to the step's descriptor as a preview through the channel; the patch is applied only on approval and recorded in the changelog.
- **The QA skill.** `skills/qa/`: given a fixture app's address and a list of expected states in plain words, walk the app, take a labeled screenshot at each step, compare each screenshot's snapshot to the expected state by the same word rule the worker uses for expectations, and produce a report as markdown with the screenshots' paths, one line per step saying met or not and what was seen.
- **Bounds.** Steps per skill, self-heal attempts per replay (one), the screenshot count.

## Tests, in the order you write them

1. Record a three-step fixture flow on the fake worker and replay it with the fake model never called.
2. Break one step (rename the element on the fixture page) and confirm a patch is proposed through the fake channel and not applied; approve it and confirm it is applied and logged.
3. The QA skill on a fixture app produces the report, with one met and one unmet state.
4. A fuzz test on the descriptor parser: any bytes, no panic.
