# Brief 5.5: browser functional tests

Before you write anything, read these five files in this order: `CLAUDE.md` for the rules and the commands, `COEUS.md` for the plain-words explanation of the state design and the check table that ties each claim to a brief and a test, `ARCHITECTURE.md` for how the code is put together and what earlier waves built, `REPO_MAP.md` for where everything lives, and `docs/COEUS_PLAN.md` for the design you are implementing, especially the section this brief names. Then read this brief and the reference files it points at. You own exactly one package. Write the tests first.

## The package

`test/functional/`, the browser flows, and `test/fixtures/site/`, a fixture web site served on a loopback port by the tests and, under `live`, on the development machine. This brief starts after briefs 5.1 and 5.2 have merged. The plan text is `docs/WORK_PLAN.md`, Part 3, Brief 5.5. You drive the whole program through the same socket the terminal uses, with the fakes from `testkit` for everything but the browser, which is the real worker under `integration` and `live` and the fake worker otherwise.

## What to build

- **The fixture site.** Static pages under `test/fixtures/site/`: a login page with a username, password, and code field that accepts one fixture credential; a compose page that posts a message and shows it; a captcha page; a page with a form for the QA skill. A tiny Go server in the test serves them.
- **The flows, each one test.** Log in to the fixture site through the vault (a fixture entry with a TOTP secret); post with a preview and approval through the fake channel; hit the captcha page and hand off, with the fake channel replying `done`; replay a recorded skill on the site with the fake model never called; the QA skill produces its report on the fixture app.
- **The live variant.** Under `//go:build live`, the same flows on all three real models against the fixture site served on the development machine, with the real worker and the visible Chrome window, and the token cost printed for `docs/PROGRESS.md`. A missing program or a daemon that is down fails loudly.

## Tests, in the order you write them

The five flows above against the fake worker, then under `integration` against the real worker, then under `live`.

## Definition of done

Everything in "Definition of done, for every package" in `docs/WORK_PLAN.md` Part 1 that applies to tests. `make check` clean on your branch. `REPO_MAP.md` regenerated. You do not touch any other package.
