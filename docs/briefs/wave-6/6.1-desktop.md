# Brief 6.1: the desktop worker and its Go side

Before you write anything, read these five files in this order: `CLAUDE.md` for the rules and the commands, `NERDGENIE.md` for the plain-words explanation of the state design and the check table that ties each claim to a brief and a test, `ARCHITECTURE.md` for how the code is put together and what earlier waves built, `REPO_MAP.md` for where everything lives, and `docs/NERDGENIE_PLAN.md` for the design you are implementing, especially the section this brief names. Then read this brief and the reference files it points at. You own exactly one package. Write the tests first.

## The package

`worker/desktop/` (TypeScript on Node with `@trycua/cua-driver`) and `internal/desktop` (Go, implementing `contract.Desktop`), one worker doing both because they share one protocol. Design section 10, "The desktop", and section 9 for the pacing and act-and-assert rules the desktop reuses. The plan text is `docs/WORK_PLAN.md`, Part 3, Brief 6.1. You build on `contract` (the desktop interface, the screenshot and mark types), `testkit` (the fake desktop, the fake channel, the fake clock), and the pattern of `internal/browser` and `worker/browser` for the process, the protocol, and the pacing.

## What to build

- **`worker/desktop/PROTOCOL.md`**, written first, in the shape of the browser one: JSON-RPC 2.0 over standard input and output, one object per line, with the methods `launch`, `screenshot`, `click`, `type`, `press`, `drag`, `clipboardGet`, `clipboardSet`, and `health`, the screenshot-with-marks shape from `contract`, and an error table.
- **The worker.** Launch or focus an application by name; screenshot the screen with numbered marks on the clickable controls found through the accessibility tree; click a mark; type with human pacing; press a key combination; drag from one mark to another; read and set the clipboard; each action followed by a settle wait and a check of the stated expectation, the same rule as the browser. Wayland and X11 both, through the driver; the display is the machine's own. Vitest and `fast-check`, coverage seventy percent, against a fixture window (a small application the tests launch, such as a text editor from the desktop's own set, or a fixture window the worker itself can open).
- **The Go side.** The `contract.Desktop` implementation over the worker's process, with the same lifecycle as the browser side: start on first use, keep alive, restart on death by exact process id. An application is granted once per session through a preview on the channel, and every action inside it that cannot be undone (typing into a field, a drag, a paste) still gets a preview through `contract.Permission`.
- **Bounds.** Method deadlines, a screenshot size cap, a cap on marks, the pacing profile.

## The borrowed designs

## Tests, in the order you write them

1. The protocol's wire tests, as in the browser worker.
2. Each action against the fixture window, one test each, including a stated expectation that is not met.
3. An ungranted application is refused; a granted one runs; an irreversible action previews.
4. The Go side passes the contract check against the fake desktop's expectations and, under `integration`, drives the real worker on this machine's display.
5. Property tests: any expectation string never throws; any bytes on standard input never crash the worker.
