Before you write anything, read these five files in this order: `CLAUDE.md` for the rules and the commands, `COEUS.md` for the plain-words explanation of the state design and the check table that ties each claim to a brief and a test, `ARCHITECTURE.md` for how the code is put together and what earlier waves built, `REPO_MAP.md` for where everything lives, and `docs/COEUS_PLAN.md` for the design you are implementing, especially the section this brief names. Then read this brief and the reference files it points at. You own exactly one package. Write the tests first.

## The package

`internal/update` and `cmd/coeus/update.go`, defining the `update` subcommand value. Design section 11, "Reliability" (updates keep the previous program and switch a link; if the new copy is not ready within sixty seconds, the link is switched back) and the goal's last words ("update itself without breaking"). The plan text is `docs/WORK_PLAN.md`, Part 3, Brief 6.3. You build on `contract` (the home's releases folder and current link), `testkit`, `internal/log` (the schema version), and `internal/reliability` (the drain marker, the backup).

## What to build

- **Check and fetch.** Read the release manifest from the configured release address (the GitHub release of brief 6.2 by default, or a local path for tests), compare the version to the running one, download the archive for this architecture, verify its checksum against the manifest, and unpack it into `releases/<version>/`. Keep the previous three releases and remove older ones.
- **Switch and verify.** Set the drain marker, wait for the running task to finish (with the marker's expiry as the limit), switch the `current` link to the new release, restart the service through `systemctl --user`, and require `/readyz` (the readiness check `serve` answers) within sixty seconds. On failure, switch the link back, restart, and report what happened.
- **Migrations.** Forward-only, numbered migrations on the one database, each in a transaction after a backup through `reliability`; they run after the new binary passes readiness, so a rollback lands on a schema the old binary understands; if a migration fails, the backup is restored and the link flips back. An older binary refuses a newer schema at start with a message naming the version to use. This package owns the migration list and the schema version the log package created.
- **`coeus update`.** `--check` prints what is available; the default installs; `--to <version>` pins; `--rollback` switches to the previous release by hand.
- **Bounds.** Download size cap, the sixty-second readiness deadline, the number of releases kept.

## Tests, in the order you write them

1. A manifest from a `testkit` server: a newer version is found, a same version is not, a bad checksum is refused.
2. A release that fails readiness (a fixture binary that exits at once) rolls back within sixty seconds on the fake clock, with a fake `systemctl` on the PATH recording the restarts.
3. A failing migration restores the backup and rolls back (integration, real database).
4. An update over a live install in a temporary home preserves every task, memory, skill, and the browser profile byte for byte (integration).
5. An older binary refuses a newer schema with the version named.
6. A fuzz test on the manifest parser: any bytes, no panic.
