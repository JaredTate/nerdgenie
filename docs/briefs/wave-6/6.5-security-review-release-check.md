# Brief 6.5: the security review and the release check

Before you write anything, read these five files in this order: `CLAUDE.md` for the rules and the commands, `COEUS.md` for the plain-words explanation of the state design and the check table that ties each claim to a brief and a test, `ARCHITECTURE.md` for how the code is put together and what earlier waves built, `REPO_MAP.md` for where everything lives, and `docs/NERDGENIE_PLAN.md` for the design you are implementing, especially the section this brief names. Then read this brief and the reference files it points at. You own exactly one package. Write the tests first.

## The work

You are a worker with fresh eyes. You have not built any of this, and you review it as an adversary would. Design section 11 is the threat list: the five safety rules, the vault, and reliability. The plan text is `docs/WORK_PLAN.md`, Part 3, Brief 6.5.

## Part one: the security review

Review, by reading the code and by writing tests that try to break it, each of: the sandbox (`internal/sandbox`: can a sandboxed command reach `~/.ssh`, the vault, the browser profile, or the home folder; can it escape the process group; can it exhaust the machine); the vault (`internal/vault`: can a value reach the log, a channel, or the model; is the key file mode enforced; is the masked prompt safe on every path); the sudo path (`internal/tool/shell` and the askpass subcommand: can escalation run without a preview; can the password leak); the network guard (`internal/tool/web`: can a fetch reach a private address by redirect, by DNS rebinding, by an IPv6 form, by a numeric host); the pairing system (`internal/signal`: can a sender skip pairing, brute-force a code, or exhaust the pending list; is the compare constant-time); and the browser profile handling (`internal/browser`: is the profile outside the sandbox and mode `0700`; can the model read cookies through a tool). Also the data marker: can a page or a file make the agent send a secret, spend money, or run something on the ask-me-first list (write a fixture that tries).

File a finding for anything that fails, as a failing test in the package's own test files plus one paragraph in `docs/SECURITY_REVIEW.md` naming the file, the line, the threat, and the fix. Fix nothing yourself unless the fix is one line; a bigger fix is a fix brief for the orchestrator.

## Part two: the release check

Run every test from every wave on a clean Ubuntu container and a clean Debian container with `make check`, through the container runtime on this machine, and `make live` on the development machine against all three models; record the results and the token costs in `docs/PROGRESS.md`. Check that `docs/PROGRESS.md` has every wave's section complete. Rewrite the README so that it explains the logic the way design section 1 does and tells a new user how to install, run `init`, link Signal, and pair, in ten lines, and check every command it names actually exists.

## Definition of done

`docs/SECURITY_REVIEW.md` exists with a section per area and a verdict; every finding has a failing test; the container runs and the live run are recorded; the README is rewritten. `make check` clean on your branch except for the failing tests that are findings, which are listed by name in your report.

## Report back

The branch name and worktree path; `git log --oneline` for your branch; the findings in severity order; the container and live results with costs; anything you could not do and why.
