## What this brief is

The security review (brief 6.5) and the first human trial (brief 3.7) were fixed by one worker per package. Each worker handed back one or two things that were right but outside its package. They are collected here, one section per package, for the fix wave after the wave 6 trial. Every item is small; every item is tests first.

## internal/contract and internal/skill: who saved a skill

`contract.Skill.Save` does not carry who is saving, so a skill the model saved from a page cannot be told from one a person saved with `/skills`. Add a `Source` to the save (person or model), keep it in the skill's front matter as `source: page` when the model saved it, and give a page-saved skill no standing approval until a person has run it once with a yes, remembered per skill. Touches the contract, the store, `internal/tool/skill`, the fake, and the wiring; the orchestrator does the contract line and the wiring, one worker does the rest.

## internal/permission: a standing approval that knows its tool and host

A skill's website approval is compiled to a pattern over the readable form, four forms per site per tool, against a session cap of a hundred. `permission.StandingApproval` should carry the tool and the host it covers, so the match is a comparison rather than a pattern and the cap counts sites. A subdomain and a port stay uncovered and go to the person.

## internal/record and internal/context: the volatile header

The record's first line carries the budget left and the cost of the turn, so every model call invalidates the prompt cache from the record onwards; on the local model that is eleven thousand tokens re-read per call. The working context must render the volatile lines after everything stable. The context worker says which function; if it is the record's printer, the record gains a second printer for the model with the header last, and the stored form stays as it is.

## internal/context: the instruction text is over its promised length

The design says the instruction text is under five hundred words; after the data marker paragraph and the layer order clause it is 648, and the fixture at a three-thousand-token window passes with thirty tokens to spare. Cut it back under five hundred without losing a rule: shorter sentences, no repeated advice, the tool list left to the tool descriptions. `MaxInstructionWords` pinned at five hundred again, the design's section 5 and the constant changed together, and the small-window fixture test given real headroom.

## internal/loop: several calls in one reply, and the checkpoint's size

The repair package already reads a list of calls from one reply, and the loop runs them in order. The instruction text must say the model may make several calls in one reply when they do not depend on each other, and the forty-step fixture gains a round with two. And a checkpoint event stores the whole record text, twenty kilobytes with a long ask, four times per tool call; store the checkpoint once per model call, and store the ask by reference to the event that first carried it.

## internal/tool/shell: an honest exit code through a pipe

The model wrote `node --test tests/ 2>&1 | tail -40`, the test run failed, and the result said "finished with exit code 0" because the pipe's last command was `tail`. The tool runs `/bin/sh -c`, and dash cannot set `pipefail`. Run the command through `bash` when it is on the machine, with `set -o pipefail` in front, and fall back to `/bin/sh` without it; failing test first: a failing command piped into `cat` reports the failing code.

## internal/channel: the same split on the terminal path

The Signal channel redacts a reply whole before splitting it, so a secret cannot straddle two messages. The terminal path streams deltas through `internal/channel/client.go` and the screen's `envelope.go`, and a secret can straddle two deltas there the same way once deltas are switched back on (they are off today because the provider's retry holds an attempt's text until it succeeds). When deltas return, redact across the delta boundary: hold back the tail of a delta that could be the start of a secret until the next one arrives, and send a reset envelope on a retry so the screen clears the partial reply. Failing test first on the fake channel.

## internal/channel: a stale message in the queue starts a task an hour later

In the live run, a prompt a screen sent an hour earlier, whose screen had since gone, was still in the queue and started a fresh task the moment the running one ended; a reply to a command from another screen was delivered to whichever screen was attached. Two rules, tests first: a queued message older than the task budget is dropped with one line in the log and a note to the next screen that attaches, and a reply to a command goes to the screen that sent it or, when that screen is gone, is kept for the next one with the command it answers named.

## internal/sandbox: the loopback

A fence with the network on can reach services on this machine; the finding is accepted for the shell tool alone until a per-namespace firewall exists. The lasting fix is a network namespace with a veth pair and a filter that allows only outbound to public addresses; it needs a helper with CAP_NET_ADMIN, which is a design decision for the orchestrator, not a worker.

## internal/tui and cmd/coeus: what the person asked for next

The first five seconds of typing can vanish on a terminal that does not answer the background-colour query: Bubble Tea's package `init` asks the terminal for its background (`OSC 11`) and reads the answer byte by byte with a five-second wait per byte, and on a terminal that never answers it swallows what the person types meanwhile. It runs before `main`, so no code of ours can move it. The fix is the Bubble Tea release that dropped the query (a dependency change the orchestrator approves, with its line in `docs/DEPENDENCIES.md`), and a test in `internal/tui` that types at one second on a pseudo-terminal that answers nothing and sees the letters.

`coeus run "prompt"` for scripting (in the wiring worker's list as item 5 of brief 3.7). A `/replay` command that shows the last replay's report. The desktop worker's screenshot inline in a handoff card was designed and is not yet seen in a trial.
