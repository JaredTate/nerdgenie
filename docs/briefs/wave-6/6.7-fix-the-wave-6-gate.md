## What this brief is

Every package that merged for waves 4, 5 and 6 was read by a reviewer with fresh eyes, code and tests, before the wave 6 human trial. Each finding below was proved with a probe that was actually run, and the probe is written out beside it so that the failing test you write first is the same experiment. One worker per package fixes only its package's findings, in order: first a failing test that reproduces the problem exactly as the reviewer proved it, then the fix. Every function under sixty lines, every file under five hundred. Rebase onto `main` first.

The live run on the local Qwen found three things: the task tool refused shapes the model writes, tool lines never reached the screen, and only a quarter of each call was served from the prompt cache. All three are still true, and findings 25, 7 and 17 are where each of them actually lives. The findings marked BLOCKING are the ones that will stall a forty-round task, spend its budget on nothing, or let something through that the design forbids.

Two notes on ownership. The three findings in "the gate itself" are fixed first, by whoever picks them up, because nothing else can be checked until `make check` is clean. And `cmd/nerdgenie/main.go` and `cmd/nerdgenie/serve.go` are the orchestrator's files, which no worker may edit: the findings that land in them — 56, 58, 60, 61, 63, 65, 71, 72, 83 and 87 — go to the orchestrator, and the worker whose package they concern writes the failing test and says in its report which line of `serve.go` has to change. ## internal/loop, the turn loop

4. **BLOCKING. A stop line the model writes about its own task fires on the first tool result that repeats two of its words.** `internal/loop/guard.go:124` `stopLineFiredBy` searches every tool result for the notable phrases of every stop line, and `guard.go:157` `notablePhrases` makes a phrase out of every pair of neighbouring words of four letters or more. The model is told to write a stop list about the work it is doing, so its stop lines name the subject of the task, and the first result that mentions the subject ends the task. Probe, against the fakes: a model writes `stop_when: ["the product notes file cannot be found"]` and then reads the notes; the read comes back "product notes: DigiByte launched…"; the task ends on round one with status `stopped` and stop line "the product notes file cannot be found". Fix: a stop condition is a statement about the world, and two words in a row are not one. Keep the phrase match for the harness's own two lines, which are about walls the harness can recognise for itself, and let the model say when one of its own lines has come true: give the task tool a `stop_now` operation naming which line fired, written in the same reply as its other calls, costing no extra call. 5. **BLOCKING. Fix: rule 4 of design section 3 says the same call is not *run* twice, and a call whose result changed is not the same call — count the run only over calls whose results came back identical, or exempt the shell tool's poll and tail actions by name.
