# Brief 8.1: the browser worker clicks a point, and a read settles after its ask

Read `docs/briefs/wave-8/COMMON.md` first. You own `worker/browser` (TypeScript, Vitest, `fast-check`, coverage above seventy percent) and its `PROTOCOL.md`, and the worker's section of `ARCHITECTURE.md`. Brief 8.2 owns the Go side at the same time; the two meet at the protocol written here, word for word.

**Part one: a click at a point.** The `click` method takes either `ref`, as now, or a point: `x` and `y`, whole numbers of CSS pixels from the top left of the page's viewport, with `expectation` required as now. A request with both a ref and a point, or with neither, or with a point outside the viewport, is refused with -32602 and a sentence saying what to send. A click at a point does what a click on an element does after the element is found: the same human pacing (`clickAgainAtItsPlace` and `clickTarget` in `actions.ts` already move the mouse and click at a place on the screen; reuse them), the same settle wait, the same diff against the snapshot before, the same expectation check, and the same result shape. A click at a point cannot retry "at its place", because it already is at its place. The `act` method's `click` step takes the same point fields, since the Go side's `browser_act` steps go through it. Reference: browser-use's coordinate click in `docs/reference/browser-use/views.py` for the shape, not the code.

Request: `{"jsonrpc":"2.0","id":3,"method":"click","params":{"x":519,"y":335,"expectation":"the info panel names Jupiter"}}`. Response: the same shape as a click by ref.

**Part two: a read settles after its ask.** `read` in `methods.ts` takes the snapshot first and evaluates the ask after, so an ask that changes the page hands back an outline from before the change. Evaluate the ask first, then wait for the page to settle the way an action does (`settle` in `settle.ts`), then take the snapshot, and hand back the answer and the outline together. The answer itself is whatever the expression returned; nothing here evaluates it twice.

**Tests first, in `worker/browser/test/`.** In a new `click-at-a-point.test.ts`, against a new fixture page in `test/pages/` that draws a planet on a canvas and, on a click at its pixels, writes the planet's name into a heading on the next animation frame: `clicks the point and reads the heading the page wrote a frame later`; `refuses a request with both a ref and a point, and one with neither`; `refuses a point outside the viewport`; `an act step can click a point`. In `ask.test.ts`: `shows the change an ask made to the page in the same read`, using the same fixture: an ask that dispatches the click, and the outline in the same read holds the new heading. The existing tests, including `hung-page.test.ts` and `expectation.test.ts`, must still pass; run the whole suite with `npm test` in `worker/browser`, and `npm run build` so `dist/` is current. Do not start a headed Chrome in tests; the harness in `test/harness.ts` already starts it headless.
