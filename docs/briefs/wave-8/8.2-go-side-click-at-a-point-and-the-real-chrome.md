# Brief 8.2: the Go side clicks a point, finds the real Chrome, and the doctor says when it cannot

You own, this wave, `internal/contract` (the browser worker interface and one new function), `internal/testkit` (the fake browser worker and its contract check), `internal/browser`, `internal/tool/browserclick`, `internal/tool/browserread` (one sentence of a description), and `internal/config` (the doctor). Brief 8.1 owns the TypeScript worker at the same time; the two meet at the protocol written in brief 8.1, word for word: the `click` method takes `x` and `y`, whole numbers of CSS pixels from the top left of the viewport, in place of `ref`. Do not touch `cmd/nerdgenie/main.go` or `serve.go`; if you need a change there, say so in your report.

**Part one: a click at a point.** `contract.BrowserWorker` gains `ClickAt(ctx, x int, y int, expectation string) (Diff, error)`, with a doc comment, beside `Click`. The fake in `internal/testkit/browser.go` answers it the way it answers `Click`, and the contract check that proves the fake and the real worker agree covers it. `internal/browser/methods.go` sends it as the protocol's `click` with `x`, `y` and `expectation`. The `browser_click` tool takes `x` and `y` beside `element`: a call names an element or a point and never both, and the refusal for neither, or both, says so in one sentence; the description tells the model that a point is for a canvas or anything the outline does not list. `browser_act`'s click step takes the same two fields and passes them through. Keep the description under forty words, which the registry enforces.

**Part two: the real Chrome.** A new function in `internal/contract`, `FindChrome() (path string, passedOver []string, err error)`, looks for `google-chrome-stable`, `google-chrome`, `chromium` and `chromium-browser` on the PATH in that order and returns the first that is not a launcher script forcing headless: a file that begins `#!` and whose text holds `--headless` is passed over and named in `passedOver`, because it gives the agent no window; the error names every candidate tried and what to install when none is left. `internal/browser/process.go`'s `workerArguments` calls it and hands the path to the worker as `--chrome <path>`, which `worker/browser/src/main.ts` already accepts; when nothing is found the worker is started as now and reports its own failure. The doctor's Chrome row in `internal/config/doctor.go` uses the same function: fine with the path it found, a warning naming each launcher passed over and why, and the missing-program warning as now when none is left.
