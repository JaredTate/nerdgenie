How Coeus gets built, from an empty folder to a working agent, in waves of five workers, with every test written before the code it proves.

The goal, and what to do if you are the orchestrator

The goal is a working Coeus: one Go binary on a Linux machine that a person can install with one script, set up with coeus init, use in a terminal, pair to their phone over Signal, and trust to use a real Chrome web browser and the Linux desktop like a person, remember what it learned, run jobs while they sleep, and update itself without breaking. Done means every wave in Part 3 has passed its gate, make check and make live are green on a clean Linux machine and against all three real models, and a person has used it after waves 3, 5, and 6 and their notes have been acted on. After wave 6 the orchestrator runs fix waves until the last trial's notes are clear.

What is left for after the goal. Other chat services (Telegram, Slack, iMessage, Discord), a web screen, voice, more than one agent, and Windows or macOS. The extension points in section 6 of the design exist so these can be added later as one new file each. None of them is built now.

If you are the AI reading this file, you are the orchestrator, and this is your instruction. Read this whole plan, then CLAUDE.md, COEUS.md, ARCHITECTURE.md, REPO_MAP.md, and docs/COEUS_PLAN.md. Then begin at wave 0 and work through every wave in order until the goal above is met. For each wave, write the briefs into docs/briefs/wave-N/, each one beginning with the first paragraph given in Part 1, and launch five Opus 4.8 workers at extra-high effort at once, one brief each. Wave 0 is the one exception and uses a single worker, because everything else depends on it. Hold every worker to the rules in Part 1: tests first at all four levels, the simplest thing that passes, plain English, one package per worker, designs ported from the reference files and never copied. When the five report back, merge, write the wiring in cmd/coeus/serve.go if the wave added anything that must be wired, run make check and make fuzz, read every new file, run make live for the wave's features, and only then move on. When something fails, write a fix brief and do not advance. After waves 3, 5, and 6, stop and ask a person to try it with the checklist in Part 1, then turn their notes into briefs. Keep ARCHITECTURE.md, REPO_MAP.md, and docs/PROGRESS.md true at every gate. Do not stop until the goal is met or a rule in Part 1 cannot be followed, in which case report exactly which rule and why.

This plan was reviewed twice by an adversarial pass. The first review found 24 blockers and the second found 15 failing checklist items; both are in docs/research/, and Part 6 says how this version answers each one. The design this plan builds is docs/COEUS_PLAN.md. The plain-words explanation of that design, with a check table that ties every claim to a brief in this plan and to a test, is COEUS.md. The comparison behind the design is docs/HARNESS_V2.md.

Part 1: The rules

These rules apply to every wave, every worker, and every line of code. A worker who cannot follow one of them stops and reports instead of working around it.

Where the work happens

All building and all testing happen on one Linux development machine, jared-irene, where this repository lives at /home/jared/Code/coeus and the five reference projects are already cloned beside it under /home/jared/Code/. The orchestrator runs there. The workers run there. The tests run there, because the sandbox, the service manager, the visible Chrome window, and the local models only exist on Linux. The machine that wrote this plan does not build anything. Wave 0 makes the development machine ready.

Who does what

The orchestrator is a Fable 5.1 model. It reads this plan, writes the brief for each worker, checks each worker's result against the brief, runs the full test suite after every wave, reads every new file, and decides whether the wave passed. It never writes feature code itself, with one exception: it owns cmd/coeus/main.go and cmd/coeus/serve.go, the two files that register subcommands and wire the packages together, so that no two workers ever edit the same file and no package ever imports a neighbor from its own wave.

A worker is an Opus 4.8 model running at extra-high effort. Each worker gets one brief, one package, and one wave. Five workers run at once. A worker never touches a package that another worker in the same wave owns, and never edits main.go or serve.go; a worker who adds a subcommand puts it in its own file under cmd/coeus/ and tells the orchestrator to register it. A worker who owns a slash command exports it as a contract.Command value and the orchestrator registers that too.

The first paragraph of every brief

Every brief begins with this paragraph, word for word, so that a worker who has seen nothing but its brief still starts with the right context:

Before you write anything, read these five files in this order: CLAUDE.md for the rules and the commands, COEUS.md for the plain-words explanation of the state design and the check table that ties each claim to a brief and a test, ARCHITECTURE.md for how the code is put together and what earlier waves built, REPO_MAP.md for where everything lives, and docs/COEUS_PLAN.md for the design you are implementing, especially the section this brief names. Then read this brief and the reference files it points at. You own exactly one package. Write the tests first.

The three living documents

Three files at the root of the repository are context for every worker and must be kept true. They follow the pattern of the HomeRecon project, where the same three files have kept a much larger codebase legible to agents for months.

  • CLAUDE.md is the first thing any agent reads. It holds the reading order, the hard rules, and the commands. It changes rarely and only by the orchestrator.
  • ARCHITECTURE.md records how the system is put together and what each wave built. Every worker whose brief changes a package's job, its interface, or its dependencies updates the matching section in the same branch. The orchestrator adds a "Wave N" section at the end of every wave, three paragraphs at most.
  • REPO_MAP.md is generated from the tree by make repo-map and never edited by hand. A drift test in make check fails if it is stale.

A worker's brief is not done until ARCHITECTURE.md is true for that package and REPO_MAP.md is regenerated.

The eight rules of the code

  1. Keep it simple. The simplest thing that passes the test is the right thing. If two designs both pass, the one with fewer moving parts wins.
  2. Build only what is needed now. No abstraction is added until the second use of it exists. No configuration option is added until a real user needs it. No feature is added because it might be useful later. The four extension points in section 6 of the design are the only places built ahead of need, and each one already has two implementations in the MVP: the terminal socket and Signal for channels, Anthropic and OpenAI-compatible for providers, built-in and user-supplied for tools, and the skills the agent learns for skills.
  3. Tests come first. A worker writes the test, watches it fail, then writes the code, then watches it pass. The commit history shows the order, and the orchestrator checks it. A test written after the code is rewritten.
  4. Go for the agent, TypeScript for the browser and desktop workers, nothing else. The Go code uses the standard library wherever the standard library will do. Every outside library is listed in docs/DEPENDENCIES.md with a one-line reason. A worker who wants to add one asks the orchestrator first.
  5. One package, one job. Each Go package has one purpose that fits in one sentence at the top of its doc.go file. A package that needs two sentences is two packages.
  6. Plain English everywhere. Every identifier says what it is. Every comment is a complete sentence. Every error message tells the reader what went wrong and what to do about it. Every log line can be read by someone who has never seen the code. The same rule applies to every document in docs/ and to the three living documents: complete sentences, technical terms explained on first use, and the glossary in Part 5 for the words that recur. The style checker in make check enforces the code half; the orchestrator enforces the document half at every gate.
  7. Bound everything. Every loop has a limit. Every wait has a timeout. Every buffer has a cap. Every outside call can fail, and the code says what happens when it does.
  8. Borrow designs, not code. The other agents are written in TypeScript, Python, and Rust. A worker reads the reference file it is pointed at, understands the design, and writes it fresh in Go. Nothing is copied line by line. The borrowed design is named in a comment at the top of the Go file, with the path to the reference, and the reference project's license is in THIRD_PARTY.md.

The four kinds of tests

Every Go package has all four before it is called done. The two TypeScript workers use Vitest for unit, integration, and functional tests and fast-check for fuzzing, at the same standard.

KindWhat it provesHow it is written
Unit testOne function does what its name says, for normal inputs, edge inputs, and bad inputsStandard Go testing, table-driven. One test file per source file
Integration testTwo or more packages work together through their real interfaces, with the real database and the real filesystem in a temporary folderIn the package that sits highest in the dependency order, marked with the build tag integration
Functional testA whole feature works the way a user would see it: a message goes in, the right reply comes out, the right things happen on diskIn test/functional/, driven through the same socket the terminal uses, with a fake model and fake outside services
Fuzz testThe code survives input it was never designed forGo's built-in testing.F, on every function that parses text from outside the program

The human trial and the visual checklist

Screens are tested by a person looking at them. After waves 3, 5, and 6, a person uses Coeus for at least ten minutes in a visible window on the development machine, never through a screenshot alone, and writes notes in docs/PROGRESS.md under the wave. The checklist:

  1. Install on a clean user account, run init, and get to the first reply without reading any document. Until the installer exists in wave 6, "install" means make install.
  2. Watch the terminal screen: first frame at once, streaming visible, an approval prompt answered inline, a masked prompt that never echoes, no flicker on resize.
  3. Link Signal, pair a phone, and have one conversation with a preview and an approval.
  4. From wave 5: watch the Chrome window while the agent logs in to a fixture site, posts with a preview, and hands off on a captcha page. The window must be visible and the pacing must look human.
  5. From wave 6: watch a scheduled job fire, watch the desktop worker open an app and type into it, and watch coeus update roll back a deliberately bad release.

Anything confusing, slow, or ugly becomes a brief in the next wave. A wave with an unfinished human trial is not passed.

The test framework and the contracts

The framework lives in internal/testkit/ and is built in wave 0, together with internal/contract/, before any feature. Every fake implements a contract interface, and every real implementation implements the same one, so the two are always written against the same lines. Every fake has a contract test that also runs against the real thing under the live tag, so fakes cannot drift.

internal/contract holds, with no dependencies: Model, Tool, Command, Channel, Permission, Memory, Skill, Job, Sandbox, Secrets (resolve a reference, get the sudo password, redact text), BrowserWorker, Desktop, Clock, Store, the record types, the configuration struct with every field and default, the exit codes, the socket message types, and the user-tool protocol.

internal/testkit holds: a scripted fake model; a fake provider server speaking both wire protocols over a local socket; a fake channel; a fake clock; a temporary home; a fake permission decider; a fake tool registry; fake memory, skill, job, sandbox, and secrets stores; a fake signal-cli, a fake search server, a fake browser worker speaking worker/browser/PROTOCOL.md over a local socket, and a fake desktop; the golden-file helper; and the forty-step fixture data. The replayer that re-runs a recorded task is built in wave 6, once the loop exists to run it.

The forty-step fixture is a scripted task with forty tool rounds, a correction at step twelve, a stop condition that fires at step thirty, and three assertions at the end: the ask and the corrections are byte-for-byte identical, the done-check passes, and every result id is still readable. In tier one it runs against the fake model from wave 1. Its live variant, the same task with a fixture web site standing in for the tools, joins make live from wave 2 and runs against all three real models at every gate after that.

Definition of done, for every package

  • Every exported function has a unit test with normal, edge, and bad inputs.
  • Every function that parses outside text has a fuzz test that runs clean for one minute under make fuzz.
  • The integration test passes against the real database in a temporary home.
  • make check reports nothing.
  • Line coverage is above ninety percent, enforced by the threshold in make check. The terminal screen and the two TypeScript workers must be above seventy, because screen code is tested by looking at it.
  • No function is longer than sixty lines. No file is longer than five hundred lines.
  • The package's doc.go has a one-sentence purpose and a paragraph a new reader could understand.
  • The borrowed design, if any, is named at the top of the file with the reference path.
  • ARCHITECTURE.md is true for the package, and REPO_MAP.md is regenerated.

Reference paths that start with ~/Code/ mean /home/jared/Code/ on the development machine, where each reference project is already cloned and wave 0 checks out the commit listed there. Wave 1: The foundation

After this wave, the event log and the record work, configuration loads, and the agent can talk to a real model provider through a fake server.

Brief 1.1: the event log. Package internal/log. An append-only table in SQLite through the pure-Go driver, holding every message, tool call, tool result, permission decision, file change, and record change, each with a sequence number, a timestamp, a task id, and a kind. Write is one insert. Read is by task, by kind, by id, or by range. A replay function hands events back in order. The database opens in write-ahead mode with one writer. Design section 4, "History." Reference: Hermes' delivery ledger at ~/Code/hermes-agent/gateway/delivery_ledger.py for "write the obligation before acting," and OpenClaw's persisted queue at ~/Code/openclaw/src/infra/outbound/delivery-queue-storage.ts. Tests: every read shape; ten thousand events replayed in order; a process killed mid-write leaves an intact log; a fuzz test on the event decoder.

Brief 1.2: the task record. Package internal/record. The record format from design section 4 as the contract types, with a parser and a printer that round-trip exactly. The rules are code: the ask, intent, and corrections are immutable after creation; a fact must carry a source; a failure must carry a cause; a step marked done must name a result; every result gets an id like r7 and its full text is stored so read r7 can fetch it; the record has four parts, goal, rules, work, and lessons; the same format serves a job record, whose plan is a list of tasks and whose results are task reports; a record is created on the first tool call; every result gets one line in the record the moment it arrives and its full text goes to the log, so the record never needs squashing; checkpoints save to the event log on every change and reload by number, which is what /tasks 17 back 3 uses; the header carries the budget line and the cost line. Reference: Prime's goal state at ~/Code/prime-agent/packages/coding-agent/src/core/goals.ts and its state with rollback at packages/coding-agent/src/core/refinement/refinement.ts; the example record in design section 4 is the golden file. Tests: round-trip on the golden record; each rule rejects a bad edit; every result readable by id; the forty-step fixture against the fake model; rewind; a fuzz test on the parser.

Brief 1.3: configuration and the home folder. Package internal/config. One file, ~/.coeus/config.toml, read once at startup into the contract struct, whose doc comments list every field and default: the model aliases with their provider, base address, and key reference; the fallback chain; the Ollama model tag; the Signal account; the browser profile path; the sandbox roots, which never include ~/.coeus itself, the vault, or ~/.ssh; the backup path; the search server address; and the caps from the design. Any wrong value produces an error naming the line. This package defines the home folder layout from ARCHITECTURE.md and provides a doctor function that reports what exists and never changes anything; init in wave 3 uses both. Tests: defaults from an empty file; every field with a wrong type; the doctor on an empty home and a full one; a fuzz test on the parser.

Brief 1.4: the model providers. Package internal/provider. Two implementations of contract.Model: the Anthropic API, and the OpenAI-compatible API with a base address, which covers OpenAI itself, Ollama, LM Studio, and every gateway. Cache markers placed where design section 4 says. Retries of three with backoff honoring the retry-after header and never on context overflow. A fallback chain from the configuration. Hermes' two local-model rules: send think=false only to Ollama-shaped addresses, and prefer the Modelfile context length. Design section 6, "Model providers," and section 4, "Working context." Reference: Prime's types and two API files at ~/Code/prime-agent/packages/ai/src/types.ts, providers/anthropic.ts, and providers/openai-completions.ts, and its overflow detection at packages/ai/src/utils/overflow.ts; OpenCode's retry policy at ~/Code/opencode/packages/opencode/src/session/retry.ts; Hermes' rules at ~/Code/hermes-agent/plugins/model-providers/custom/__init__.py and agent/model_metadata.py. Tests: both APIs against the fake provider server, including streamed tool calls, a stalled stream, a rate limit with retry-after, a server error, and an overflow; the fallback chain moves on; the contract test under live against all three real models; a fuzz test on the stream parser.

Brief 1.5: tool-call repair. Package internal/repair. Takes the raw text of a reply and returns the tool calls in it, whether they arrived structured, as JSON in a code fence, as a <tool_call> block, or as a near-miss on a real name; fixes names that are close; returns a plain error naming the real tools otherwise; after two failed parses in a row, the text is the answer. Design section 3, rule 5. Reference: ZeroClaw's parser at ~/Code/zeroclaw/crates/zeroclaw-tool-call-parser/src/lib.rs; OpenClaw's grammar at ~/Code/openclaw/packages/tool-call-repair/src/grammar.ts; OpenCode's invalid-call path at ~/Code/opencode/packages/opencode/src/tool/invalid.ts. Tests: a golden file per envelope shape; name repair; the two-failures rule; a fuzz test that never panics.

Wave 2: Context, permissions, the sandbox, secrets, and the tools

After this wave, every tool exists and runs safely, and the prompt can be built for any model. Nothing here imports a wave-2 neighbor: the tools code against contract and the fakes.

Brief 2.1: the working context builder. Package internal/context. The layered prompt from design section 4: the harness rules, the persona, the tools, the job summary when the task belongs to a job, the stable part of the record, the live part, pinned evidence, recent messages, the memory hint. The model instruction text from design section 5 is a constant here, and a test asserts it stays under five hundred words. Window sizes come from the model's context length by the one rule in the design. When the window is full, the oldest result's full text leaves the window; its line in the record and its copy in the log stay, and read r7 brings it back. Nothing above the cache line changes during a task. The cost line is written every turn from the provider's token counts. Reference: Hermes' tiers and cache points at ~/Code/hermes-agent/agent/prompt_caching.py and agent/prompt_cache_boundary.py; OpenClaw's cache boundary in ~/Code/openclaw/src/agents/system-prompt.ts (search for SYSTEM_PROMPT_CACHE_BOUNDARY); Hermes' verbatim user messages in ~/Code/hermes-agent/agent/context_compressor.py; OpenCode's re-read of instruction files at ~/Code/opencode/packages/opencode/src/session/instruction.ts. Tests: a golden prompt for a 24k model and a 200k model from the same task; nothing above the cache line changes across ten turns; every result that has left the window is still readable by id; the cost line matches the fake provider's counts; under live, the same task on all three models produces a prompt within each model's window.

Brief 2.2: the permission function. Package internal/permission. The contract.Permission implementation: rules of tool, pattern, and action from the policy file; last match wins; default allow; the ask-me-first list, shipped with three entries (bulk or recursive deletes such as rm -rf, sudo, spending money) that the user can change or empty; shell commands reduced to a readable prefix; the answers once, always for the session, and reject with a reason; anything on the list produces a preview; standing approvals attached to skills with a limit and an expiry; an unattended run that hits the list stops and reports. Design section 11, rule one. Reference: OpenCode's engine at ~/Code/opencode/packages/opencode/src/permission/index.ts, rule format at packages/core/src/v1/config/permission.ts, prefix table at permission/arity.ts; Hermes' unattended rule in ~/Code/hermes-agent/tools/approval.py. Tests: a table of rules and calls; prefix reduction; each of the three default entries; an empty list allows everything; an expired standing approval; an unattended run that hits the list stops and reports; a fuzz test on the pattern matcher.

Brief 2.3: the sandbox. Package internal/sandbox, implementing contract.Sandbox. Wraps a command in bwrap with a Landlock ruleset and a seccomp filter; the roots come from configuration and never include ~/.coeus, the vault, the browser profile, or ~/.ssh; network is allowed; the package reports itself unavailable if bwrap is missing. Design section 11, rule two. Reference: ZeroClaw's wrapper at ~/Code/zeroclaw/crates/zeroclaw-runtime/src/security/landlock.rs and trait at security/traits.rs; Codex's rules at docs/reference/codex/landlock.rs. Tests: a sandboxed read of ~/.ssh fails; a sandboxed write to ~/.coeus fails; a sandboxed network call succeeds; unavailable without bwrap.

Brief 2.4: the vault, sudo, and redaction. Package internal/vault, implementing contract.Secrets. Part 4: What the orchestrator watches for

  • A worker adds a library because it is convenient. Reject unless the reason is in docs/DEPENDENCIES.md and the standard library cannot do the job.
  • A worker writes the code first and the test after. The commit history shows it. Reject.
  • A worker copies code instead of porting the design. Rust and TypeScript idioms in Go are the sign. Reject and point at the reference again.
  • A worker builds ahead of need. A flag, an option, or a layer nobody asked for is removed before merge.
  • A package imports a neighbor from its own wave. The build order in Part 2 is the law. Move the shared piece to contract or the join to serve.go.
  • A package grows past its one sentence. Split it before the next wave.
  • A test passes by accident. The orchestrator changes one thing the test should catch and confirms it fails.
  • A fake drifts from the real thing. The contract tests under live catch it at the gate.
  • The prose slips. The style checker runs in make check for code; the orchestrator reads the documents at the gate.
  • The living documents go stale. REPO_MAP.md drift fails make check. ARCHITECTURE.md is read against the code at every gate.
  • A human is never asked. Waves 3, 5, and 6 each end with a person using it. No exceptions.
  • A live test skips. A missing key is a failure, not a skip.

Part 5: Glossary and the code bases to read

Words that recur. A harness is the program around the model. A turn is one exchange from the user's message to the agent's reply. A tool call is the model asking the harness to run a tool. The record is the task's state, shaped like an operations order. Working context is what the model sees on one call. A fake is a stand-in for a real service, used in tests. A contract is an interface two packages share. A wave is one round of five briefs. A gate is the set of checks a wave must pass. The sandbox is the fenced-off area a command runs in.
