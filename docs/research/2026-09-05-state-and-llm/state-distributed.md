# State in blockchains and distributed systems: what Nerd Genie can borrow

Nerd Genie keeps three things apart: a log of everything that happened, a small task record of what is true now, and a working context built fresh for every model call. Blockchains and distributed systems solved the same split at planet scale, because thousands of computers must agree on a state without any of them replaying the world from the beginning. This report turns their state tricks into concrete ideas for an agent whose memory must fit in a record a person can read.

A few words used throughout. A **hash** is a short fingerprint of some data, usually 32 bytes, that changes completely if one bit changes. A **log** is a list only ever added to at the end. A **checkpoint** is a saved copy of the state at one moment. A **node** is one computer in a network. **Replay** means feeding the log back through the same program to rebuild the state. A **replica** is one copy of a program that several machines run in step.

## 1. Top ideas, ranked by likely impact

**1. Make the record the compacted log: every write goes to a named slot, and the last write per slot wins.** zkSync, a system that runs on top of Ethereum, does not publish its transactions to Ethereum; it publishes *state diffs*, the list of storage slots that changed and their new values, so a slot written ten times costs one entry. Apache Kafka's *log compaction* keeps "at least the last known value for each message key". Nerd Genie's record already has stable keys: `r7`, `D1`, `F1`, `C1`, plan step 3, done line 2. If the log stores each `task` tool call as (slot, new value) and the harness defines the record as "the last value of every slot," then the record is a pure function of the log and can never drift from it. A withdrawn plan step is a *tombstone* (a null value) that stays in the log. Risk: small models will write to the wrong slot sometimes, so the tool must name the slot back. Sources: zkSync data availability docs; Kafka design, "Log Compaction".

**2. One pure reducer, so the log replays as a test and a rule change re-evaluates every past task.** Redux, a state library for web apps, insists that the only way to change state is to emit an action, and that a *reducer* (a function with no side effects) turns the old state plus the action into the new state; because of that, actions "can be logged, serialized, stored, and later replayed," and in Redux DevTools "if you change the reducer code, each staged action will be re-evaluated." Temporal, a workflow engine, throws a *non-deterministic error* when replayed code stops matching its history. Nerd Genie should hold every record change in one function `apply(record, event) -> record` with no I/O. A change to the record rules is then tested by replaying every stored log and comparing to the stored checkpoints; every difference is either a bug fixed or a bug introduced, and the diff says which. Risk: the function must never read the clock or the file system; the harness-owned "situation" lines must come from logged events, not live checks. Sources: Redux three principles; Redux DevTools README; Temporal workflow definition.

**3. Continue-as-new: when the record is full, roll the task into a fresh one that carries only the state it needs.** Temporal terminates a workflow whose history passes 51,200 events or 50 MB; its answer is *Continue-As-New*, which "completes the current Workflow instance and atomically starts a new one with the same Workflow ID" and a new history, passing "the latest relevant state" as the new input. Nerd Genie already refuses a record write past three thousand tokens; continue-as-new gives that refusal a mechanism: the harness closes task 17 with a report, opens task 18 in the same job, and carries over exactly the goal, the corrections, the stop list, the lessons, the open done lines, and a pointer to the old record. Temporal's warning: drain pending signals first, or they are lost, so the message queue must be emptied into the new record before rollover. Sources: Temporal limits and continue-as-new docs; Durable Functions eternal orchestrations.

**4. A state root: hash the record at every checkpoint, chain it to its parent and to the log offset, and print it in the header.** Ethereum's yellow paper keeps the whole world state in a tree whose root hash "can be used as a secure identity for the entire system state." Git names every object by the hash of its content, and each commit points at its parent, so history cannot be edited unnoticed. For Nerd Genie: checkpoint `c17.42` gets a hash over the canonical record, the parent checkpoint's hash, and the log position. That gives tamper evidence, a one-line answer to "are these two processes looking at the same state," a cheap check that a replay rebuilt the same record, and content addressing for results: the same tool call with the same arguments produces the same blob, so the "never run the same call twice" rule becomes a cache hit that returns the old id. Risk: the canonical form must be fixed before the hash is trusted; the hashing itself is free. Sources: Ethereum yellow paper section 4.1; Pro Git, "Git Objects".

**5. Assume-valid resume: load the checkpoint and start work at once; verify it against the log in the background.** Bitcoin Core's *assumeutxo* ships a hash of the set of unspent coins as of a recent block; a new node loads a matching snapshot, "postpones verifying old block chain history until after the user is able to receive recent transactions," then verifies the old blocks "so that it could eventually prove that the hash it first started with was correct." Ethereum's consensus clients do the same with *checkpoint sync*: Nimbus says syncing from genesis "can take several days" and a checkpoint gets you started "in minutes." Today's plan replays the whole log after a crash. Better: load the last checkpoint, answer the user now, and replay the log in a background goroutine, comparing the rebuilt record's hash (idea 4) to the checkpoint's; on a mismatch, stop the task and tell the user. Risk: a corrupt checkpoint is trusted for a few seconds; the mismatch check bounds the damage. Sources: Bitcoin Optech, AssumeUTXO; Bitcoin Core 28.0 notes; Nimbus trusted node sync.

**6. Two kinds of proof on the done list: validity-proved lines and optimistic lines with a challenge that re-runs one step.** *Optimistic rollups* post results to Ethereum and assume they are right unless someone submits a *fraud proof* within a challenge window of about seven days; when challenged, "the L1 chain only needs to re-execute one step in the rollup's execution," found by bisection. *ZK rollups* instead attach a *validity proof* that is checked at once, with no window. Label each done line: `[v]` when the harness itself checked it (a file exists, a test passed: a validity proof) and `[o]` when the model judged that result r12 satisfies it (optimistic). Let the user challenge an `[o]` line by id, and have the harness re-run only the one command or check behind that result, never the task. Risk: browser results cannot be re-run, only re-shown; a challenge on those is a screenshot. Sources: ethereum.org optimistic rollups and ZK rollups.

**7. Stable checkpoints and water marks: only a verified checkpoint is a rewind target, and the window is what lies above it.** In Practical Byzantine Fault Tolerance (PBFT), a way for replicas to agree even when some lie, each replica keeps a message log that would grow without bound; every W requests it takes a checkpoint and, once 2f+1 replicas confirm the same state digest, the checkpoint is *stable* and the replica "discards all entries in its log with sequence numbers less than or equal to" it. A replica holds only the window between the *low-water mark* (the last stable checkpoint) and the *high-water mark*. Nerd Genie's working context is exactly that window: everything below the last stable checkpoint is represented by the record alone; everything above it rides in full. A checkpoint is stable when the background replay (idea 5) confirms it, `/tasks 17 back 3` moves only between stable checkpoints, and the "recent results" section is defined as the log above the low-water mark. Risk: none new; this names a rule the design already half has. Source: Castro, PBFT thesis, sections 2.3.4 and 5.3.

**8. Channel settlement with a sequence number: the working context is off-chain chatter, the checkpoint is the settled state, and a stale write is refused.** A *payment channel* lets two parties trade signed state updates privately and touch the blockchain only to open, close, or dispute; each update carries a nonce, "newer states trump older ones," and in Lightning "any broadcast of older transactions will cause a violation of the contract, and all funds are given to the other party as a penalty." For Nerd Genie: every prompt carries the checkpoint number it was built from; every `task` tool call is stamped by the harness with that number; a write built on an older checkpoint than the current one (because a user correction landed mid-turn) is refused and the model gets the fresh record. That closes the race between the harness's writes and the model's. Cost: one integer per call, filled by the harness. Sources: ethereum.org state channels; Lightning Network paper, section 3.

**9. Light-client reports: every claim the user sees carries a proof id, so the user verifies with one command instead of reading the transcript.** Bitcoin's *simplified payment verification* lets a phone keep only block headers, 80 bytes each, "4.2MB per year," and check a payment by "the Merkle branch linking the transaction to the block." Ethereum's `eth_getProof` lets a client verify any account against a 32-byte state root offline. The user of Nerd Genie is a light client. The report sent over Signal ("what changed, what was checked, what is left") should carry the ids: "posted, 236 characters (r14); under 280 checked by the harness (r6); checkpoint c17.42 a3f9…." Risk: ids in a chat message look like noise to some users; keep them at the line ends, as the record already does. Sources: Bitcoin whitepaper section 8; EIP-1186; ethereum.org light clients.

**10. CRDT-shaped sections: give each part of the record a merge rule, so writes from two writers never conflict.** A *conflict-free replicated data type* is a structure whose copies can be edited independently and always merge to the same result, because merging is order-free and repeat-safe (`merge(a,a)=a`). The record's parts already fit known types: corrections, results, decisions, and failures are grow-only sets; each plan step and done line is a last-writer-wins register keyed by number, with the checkpoint sequence as the tie-breaker. That buys three things: harness and model can write in the same turn without ordering rules, a replayed event applied twice is harmless, and two sub-agents working parts of one job on different machines can hand back records that merge without a coordinator. Risk: last-writer-wins on a plan step can silently drop a concurrent edit; log both, show both. Sources: crdt.tech and its glossary.

**11. Checkpoints as a DAG, not a line: a rewind is a branch, and the abandoned path stays in the log.** Git commits point to parents; a branch is just a name for a commit, and checking out an old commit and committing again makes a fork, not an erasure. `/tasks 17 back 3` should create checkpoint `c17.43` with parent `c17.39`, leaving `c17.40` to `c17.42` in place. The after-action review can then compare the two paths, and a failure on the dead branch is still a lesson. Cost: one parent field per checkpoint. Risk: the side panel must show which branch is live. Source: Pro Git, "Git Objects".

**12. Rent: print what every line costs, and demand a deposit before the record may grow.** On Solana every account must hold "a refundable minimum lamport balance proportional to its data size to remain onchain," computed as (size + 128 bytes) × 3,480 lamports per byte-year × 2 years. A record line's rent is its tokens times the calls left in the task. Nerd Genie should show each section's token count in the header, make the size refusal name the section with the highest rent, and require the deposit the design already implies: no plan and no results until the why and the done list exist. Rent here is information, not eviction; the record throws nothing away. Risk: header numbers cost tokens on every call; keep them to one line. Source: Solana accounts docs.

## 2. Findings

**Bitcoin's UTXO set.** Bitcoin has no accounts. Its state is the set of *unspent transaction outputs* (UTXOs): every coin that has been created and not yet spent, each with an amount and an owner. A payment destroys some UTXOs and creates others. The whitepaper already planned for a small state: "once the latest transaction in a coin is buried under enough blocks, the spent transactions before it can be discarded." DigiByte kept this model. Lesson: state that is a set of independent facts, each spent exactly once, is easy to prune and easy to check. The record's results and corrections are UTXO-like: added once, never edited.

**Ethereum's accounts and why it switched.** Ethereum's whitepaper says a UTXO "can either be spent or unspent; there is no opportunity for multi-stage contracts or scripts which keep any other internal state." So Ethereum made the state a map from addresses to accounts, each with a counter, a balance, and storage. Lesson: when work has stages, you need mutable slots with a counter, which is what plan steps and done lines are.

**World state, Merkle-Patricia tries, and state roots.** The yellow paper defines the world state as a mapping "though not stored on the blockchain" but kept in a trie whose root hash "can be used as a secure identity for the entire system state." Every block header carries that 32-byte root. A *Merkle proof* is the handful of hashes from a leaf up to the root; "it is impossible for an attacker to provide a proof of a (path, value) pair that does not exist." Light clients "only process block headers" and check each value they fetch against the root. Lesson: commit to everything with one hash, and give readers proofs, not copies.

**Rollups: state diffs versus full replay, fraud proofs versus validity proofs.** Optimistic rollups wait about seven days for a fraud proof and bisect a dispute down to one step; ZK rollups attach a validity proof checked at once. zkSync goes further and posts only state diffs: "changes to the same storage slots across multiple transactions can be grouped." Lesson: publish the diff, not the transcript; accept claims with a challenge path; prefer a cheap direct check where you can.

**State channels and payment channels.** Two parties lock funds in a contract, then exchange signed state updates privately with a nonce on each; the chain sees only the open, the close, and any dispute, where "the honest party provides the latest valid state." Lightning enforces "broadcasting only the most recent transaction" with a penalty. Lesson: keep the chatter off the settled state, number every state, and make presenting stale state costly.

**Pruning, snap sync, and checkpoint sync.** Geth's full sync, replaying from the first block, took 8 to 10 days; fast sync fetched about 675 million trie nodes one by one, 1.75 million round trips; snap sync downloads contiguous ranges of state with range proofs and rebuilds the trie locally. Consensus clients start from a *weak subjectivity checkpoint*, a state root "all nodes on the network agree belong in the canonical chain," obtained socially and checked "against several independent public sources." EIP-4444 has nodes stop serving history older than 33,024 epochs, about a year, because history "currently occupy[s] more than 400GB." Lesson: nobody serious replays from genesis any more. Start from a trusted small state, verify in the background, hand new nodes ranges with proofs, and let old history move to cold storage while ids remain resolvable.

**DigiByte's design choices.** DigiByte is "a pure proof-of-work UTXO chain" built on Bitcoin Core (Core v8.26 on the Bitcoin Core 26 framework, with Taproot), with 15-second blocks, five mining algorithms that "each average out to mine 20% of new blocks," DigiShield difficulty re-targeting every block (activated at block 67,200 in February 2014, later adopted by Dogecoin and Zcash), and "twelve years live, zero downtime." Lesson: DigiByte scaled by tightening the loop and spreading trust across five independent checkers, not by changing the state model. Nerd Genie's equivalents: a checkpoint on every change, several independent proofs on the done list. I found no DigiByte document about state size or pruning beyond what it inherits from Bitcoin Core.

**Solana's accounts and rent.** Solana is a key-value store: every address maps to an account with a balance, data, an owner program, and an executable flag; code and data live in separate accounts, and "only the account's owner program can modify its data." Accounts must hold a refundable rent-exempt deposit proportional to size, capped at 10 MiB. Lesson: separate code (skills) from data (tasks), make one owner per slot, and put a price on bytes.

**CRDTs and eventual consistency.** A CRDT lets "users modify the data on any replica independently of any other replica, even if the replica is offline," and guarantees convergence with no coordinator, either by shipping whole states through a merge function (state-based) or by shipping operations that can be applied in any order (operation-based). Lesson: choose data types whose merge is obvious, and idempotent replay comes for free.

**Byzantine fault tolerance.** PBFT keeps a service correct with up to f faulty replicas out of 3f+1. Its log "would grow without bound," so every W requests each replica takes a checkpoint, and 2f+1 matching digests make it stable, after which everything below is discarded; slow replicas catch up by *state transfer* of a checkpoint rather than by message replay. Lesson: a checkpoint several checkers agree on is safe to truncate below.

**Deterministic replay from a log.** Jay Kreps' 2013 essay states the state-machine replication principle: two identical deterministic processes given the same inputs in the same order end in the same state, so the log "squeezes all the non-determinism out of the input stream" (the page is unreachable today; quotes via search excerpts). Temporal and Durable Functions rebuild a workflow by re-running its code against the history, and both demand deterministic code. This is the agent problem exactly: Temporal records "all inputs and returns of Activities" in history, and an agent's tool results are its activities. Ably's engineering note on Temporal chat agents reaches Nerd Genie's own conclusion: "keep the transcript outside Temporal's event history entirely," keyed by conversation id, not run id. Microsoft's event-sourcing guidance adds that snapshots "are an optimization, not a replacement for the eventstream" and that events should record intent ("two seats were reserved"), not resulting state ("remaining seats changed to 42"). Lesson: the log holds intent, the reducer is pure, the checkpoint is a cache, and large payloads live beside the log with an id.

**Continue-as-new.** Temporal's and Durable Functions' answer to unbounded history is not summarization but rollover: close the run and start a new one under the same id with the state passed as input. Lesson: a task that outgrows its record gets a successor, not a squeeze.

**Git as a content-addressed store.** Git "is a content-addressable filesystem": blobs, trees, and commits are named by the hash of their content, a commit names one tree and its parents, and an object graph is verifiable from the tip. Lesson: results by hash, checkpoints as commits, rewinds as branches.
