## B. Internal contradictions

1. **Diff vs. fresh snapshot.** §2 decision 2: "the browser returns the snapshot diff." §7: "Each returns what changed **plus the fresh snapshot**." §7 diagram: "Return diff + fresh snapshot, **~200 tokens**." §7 text: "What the model sees, **about 1,500 tokens** at most." A fresh 1,500-token snapshot cannot be a 200-token result, and returning it makes decision 2's "diffs, not dumps" a dump with a diff header.
2. **"No compaction" vs. folding.** §5: "There is no compaction step." Same paragraph: "the harness folds 'done' items into one line. Old browser results collapse to a one-line summary; only the last two snapshots stay." That is compaction. And the state file's "done / next / open questions" can only be written by the model (§4 diagram F: "Reply. Update state file"), so decision 1 replaces "summaries that lose things" with a model-written rolling summary every turn.
3. **Prefix arithmetic.** §5: prefix "~2,000 tokens" = identity + style + 15 tools + 9 deferred names. §10: 150–220 tokens per tool, "about 2,000 for the fifteen core." 15 × 150 = 2,250 before anything else is added.
4. **"Under 8,000 tokens, always."** §5 caps: prefix ≥2,250 (B3) + role files 7.6k chars (~1,900 tokens) + state file up to ~1,000 + hint 150 + last 4 exchanges with two verbatim snapshots (≤1,500 each) and tool results (≤4,000 chars ≈1,000 each) ≈ 9,000–10,000. "Always" cannot hold at the plan's own numbers.
5. **Style rule length.** "74 words" (twice) vs. 73 in the quoted text.
6. **Scope of the small model.** §2 decision 3: the small model "handles quick questions, memory hints, summaries, and loop-guard chatter." §18: "Start narrow: commands and exact skill triggers only" (which decision 3 says need no model at all). §1 diagram routes only "command or skill" and "real task"; "quick question" has no edge. §17 puts "small-model routing" in v3 and a "local-model ladder" in v5, so the decision headlined as new is deferred twice.
7. **Loop rule 3 counts.** "Same call twice… do not run it; return 'Same call as the last two.'" ## C. Simplicity (KISS)

### The nine decisions

1. **State file instead of history.** Not simplest. It is a rolling summary the model must rewrite every turn (output tokens every turn; a new way to drop a fact). Simpler with nothing lost: pin the original ask verbatim, keep the turn's messages, trim old tool results to one line (already in §5), compact at a threshold quoting user messages verbatim (Hermes). One mechanism, already proven.
2. **Diffs, not dumps.** The browser "diff" is redundant once the fresh snapshot with `[new]` and a `changed:` header is returned (§7 does this). Shell tail + exit code and file "changed region" are ordinary truncation. Keep the header, drop the separate diff and the 3–10× claim.
3. **Small model first.** Text-matched commands and triggers are the win and cost nothing. A second inference path for "quick questions, hints, summaries, chatter" adds a second prompt, a second failure mode, and GPU contention with the main local model (Hermes added `review_idle_queue.py` for exactly this). Simpler: one model at a time (`/model`), text routing only, memory hint from FTS5 with no model. Add the second model when the memory test or cost log shows a need.
4. **Act and assert.** Simplest thing that meets "reliable browser"; keep. Make `expect` optional and let the harness's own `changed: nothing` flag do the work; small models will not write expectations every step.
5. **One event log; every failure becomes a test.** Keep the log. "Every failure becomes a test" holds only for deterministic tools; browser and shell replays need fixtures (§15 already has them). Cut the claim to that.
6. **Preview first.** Keep; it is the cheapest safety mechanism in the document. State the one exception (skill standing approvals) and delete the separate "standing approvals" concept.
7. **Learn once, run as code.** Right idea; too much machinery for v1: two skill formats (`steps.yaml`, `run.sh`), `test.yaml`, `CHANGELOG.md`, self-heal proposals with approval, a three-heal counter. Simpler: one recorded format plus a dry-run flag; a failed replay wakes the model (already the rule) and the model re-records. Add self-heal after a month of replays.
8. **Harness writes memory.** Cheap and good for files/commands/sites (it is the event log anyway). The "no / actually / always / never / don't" trigger will capture chatter and secrets ("No, the gate code is 4321" lands in plaintext memory with no redaction rule). Simpler: capture a correction only when the model's previous reply is contradicted, or on `/memory add`.
9. **Skills carry their own permissions.** Simplest and best; keep. This *is* the standing-approval mechanism; merge the two.

### Mechanisms

- **State file:** replace with pinned ask + normal trimming (decision 1).
- **Reflex/cortex routing:** text routing only in v1; no second model (decision 3).
- **Event log as the only source of truth:** keep the append-only `events` table; do not force jobs and deliveries into "views" of it. Cron needs mutable rows (`next_run`, `locked_at`); ZeroClaw's `cron_jobs` claim-lock shape is the proven answer. Two small mutable tables beside the log is simpler than materialised views.
- **Review fork (16 steps after real work):** a second model run per task doubles cost on cloud and GPU time locally; Hermes gates it heavily for that reason. v1: no fork; one prompt line ("save durable facts with `memory save`") plus harness capture. Add the fork only if the monthly memory test shows gaps.
- **Nightly consolidation (local model proposes merges):** skip in v1, as R12 recommends; the 2.2k cap already forces curation and a third writer to MEMORY.md is a new bug class.
- **Standing approvals:** fold into skill permissions; one concept, one enforcement point.
- **Taint:** keep; one bit per turn. Define the cron/skill case in one sentence (recommend: unattended runs at `ask` fail closed with a Signal message, R09).
- **HMAC receipts:** over-engineering for a single Go process that builds every tool-result message itself; the dispatcher can refuse any tool result it did not produce by construction. ZeroClaw needs receipts because results cross sub-agents and channels. Drop.
- **Three-way element cascade (role+name → CSS → text/near-text):** start with role+name then visible text; CSS selectors are what drift. Add the third level when fixtures show a need.
- **Personas (`jt`, `work`, `scratch`):** three Chrome profiles, three long-lived workers, three vault scopes on day one. Same home IP and machine link them anyway, so "one ban does not take the others" is weak. v1: one persona plus an ephemeral headless context for public reads; add `work` when a work account exists.

### Over-engineered for one user maintained by one person and Claude

- Nine "decisions" where 1, 2 and 8 are one idea (fewer tokens per turn) and 6 and 9 are one idea (skill-scoped approval).
- Five overlapping token-saving mechanisms (state file, diffs, small model, tool deferral bridge, memory hint) each with its own knobs, before any token measurement exists.
- 24 tools. `web` (fetch without login) is redundant with the browser under the "browser like a human" rule; `message` duplicates the reply; `ask_user` duplicates a plain-text question (Hermes's A/B showed models fall back to text questions, which on Signal is the same UX); `tool_search` exists only because there are 24 tools. About 14 would do: read, write, edit, search, shell, memory, skill, schedule, browser_open/read/click/type/act/handoff (fold `browser_login` into `handoff`/`act`), computer.
- HMAC receipts (above).
- Signed manifest + `releases/<version>` + symlink flip + supervisor rollback for a binary built on the same box. Keep "health-check, keep the previous binary, flip back"; drop signing and the manifest until there is a second machine.
- Two thread watchdogs + `WatchdogSec` + `/readyz` + crash-loop breaker + lifecycle sentinel. Hermes needed OS-thread watchdogs because asyncio and the GIL can freeze the loop; Go has neither problem. `WatchdogSec` fed from the main loop plus `Restart=always` plus the crash-loop breaker is enough.
- `delegate` (sub-agents) for a single-user, one-task-at-a-time agent. Defer indefinitely.
- Nightly self-check that opens every logged-in site at a fixed hour: a daily, same-time, automated login check is the bot signature the human-pacing section is trying to avoid. Check on use, not on a timer.
- Skill self-heal with approval and a three-heal counter in v3.
- Six diagrams for 5,400 words; §3's diagram repeats §3's table.

### Missing against the user's explicit asks

- **sudo:** no path exists that works. `bwrap` + `no_new_privs` blocks setuid `sudo` inside the sandbox (B12). Needed: a separate, previewed, non-sandboxed `sudo` action with `SUDO_ASKPASS`, or run privileged commands via a `systemd-run`/polkit helper.
- **Network for CLI tools:** "any CLI tool" (`gh`, `curl`, package managers) needs egress; the sandbox section never says whether sandboxed children get network, and R09 defaulted them to none.
- **Linux desktop like a human:** "every action needs approval" makes it supervised clicking; no per-app or per-session grants, no pacing profile, no app launch, no clipboard. Visual QA "on screen" has no act-and-assert path; only the browser does.
- **Inbound Signal attachments:** JT sending a photo or screenshot is unspecified (`message` is outbound only), and the ZeroClaw channel named as the source does not download attachments.
- **Watching the browser remotely:** no `/screen` or "send me a screenshot" command; TUI display of screenshots (Kitty/iTerm protocol) unmentioned; the headed-window-on-a-locked-desktop question (§18) is central to overnight jobs and unresolved.

- **Local model details:** which Ollama/LM Studio model `/model local` means, and the `num_ctx`/prefix-cache rules R03 and R14 flagged (byte-stable prefix, fixed `num_ctx`) are absent.
